Why SQL formatting matters

Same query, same result — but one you can debug and one you can't.

SQL doesn't care about whitespace. The database engine parses the query, finds the keywords, and runs the logic. Indentation, line breaks, uppercase — none of it affects execution. A 400-character one-liner runs exactly as fast as a formatted query with 15 lines.

The gap is for humans, not machines. When you're reading a query you wrote six months ago, or reviewing a colleague's pull request, or debugging why a report is returning wrong numbers, the formatted version is what makes the difference. A line like this: 

select p.name, p.price, s.name as supplier, count(o.id) as order_count from products p join suppliers s on s.id = p.supplier_id left join order_items oi on oi.product_id = p.id left join orders o on o.id = oi.order_id and o.status = 'paid' where p.quantity < 10 and p.price > 20 group by p.id having count(o.id) > 5 order by order_count desc

...is impossible to review. Is the o.status = 'paid' condition part of the JOIN or part of the WHERE? Does the group by include the right columns? The having clause — is it filtering the count correctly? With everything on one line, you can't tell at a glance.

Formatted, the same query becomes: 

Select p.name, p.price, s.name As supplier,
Count(o.id) As order_count
From products p
Join suppliers s On s.id = p.supplier_id
Left Join order_items oi On oi.product_id = p.id
Left Join orders o On o.id = oi.order_id
And o.status = 'paid'
Where p.quantity < 10
And p.price > 20
Group By p.id
Having Count(o.id) > 5
Order By order_count Desc

Now the JOIN conditions are clearly attached to their JOINs. The o.status = 'paid' is visibly part of the orders JOIN, not the WHERE. The AND conditions are indented under their parent clause. The whole structure is visible.

The bug-spotting difference is real. A formatted query shows a missing JOIN condition immediately — the ON clause is empty. A formatted query shows an accidental AND where you meant OR. A formatted query shows a GROUP BY that's missing a column. Unformatted, all three hide in plain sight.

How the formatter works

40 lines of JavaScript. No dependencies. Readable in 2 minutes.

The formatter does four things, in order: normalize (collapse whitespace, uppercase keywords), break (split on major clause keywords), indent (put AND/OR under the parent clause), and assemble (join with newlines). Every step is a single regex or string operation. No parsing tree, no dialect awareness, no validation — just text transformation. 

var SQL_KEYWORDS = [
'SELECT','FROM','WHERE','JOIN','LEFT JOIN','RIGHT JOIN',
'INNER JOIN','OUTER JOIN','GROUP BY','ORDER BY','HAVING',
'LIMIT','OFFSET','INSERT INTO','VALUES','UPDATE','SET',
'DELETE','CREATE TABLE','ALTER TABLE','DROP TABLE',
'AND','OR','ON','AS','DESC','ASC','COUNT','SUM','AVG',
'MIN','MAX','DISTINCT'
];

function formatSQL(sql) {
// 1. Normalize: collapse whitespace
sql = sql.replace(/\s+/g, ' ').trim();

// 2. Uppercase keywords
SQL_KEYWORDS.forEach(function (kw) {
var re = new RegExp('\b' + kw + '\b', 'gi');
sql = sql.replace(re, kw);
});

// 3. Break on major clauses
var major = ['SELECT','FROM','WHERE','JOIN','LEFT JOIN','RIGHT JOIN',
'INNER JOIN','GROUP BY','ORDER BY','HAVING','LIMIT','OFFSET',
'INSERT INTO','VALUES','UPDATE','SET','DELETE'];
major.forEach(function (kw) {
var re = new RegExp('\b' + kw + '\b', 'g');
sql = sql.replace(re, '\n' + kw);
});

// 4. Indent AND/OR under their parent clause
sql = sql.replace(/\b(AND|OR)\b/g, '\n $`1');

// 5. Clean up leading newlines and extra spaces
return sql.replace(/\n\s+\n/g, '\n').replace(/^\n+/, '').trim();
}

That's the whole algorithm. Four steps, each a regex. The formatter doesn't try to be smart — it doesn't know what a JOIN condition is or where a subquery starts. It knows what the keywords are, and it uses them as anchors to insert line breaks and indentation.

What this trades off: the formatter will occasionally misindent a complex query with subqueries or CTEs. It won't preserve any formatting you've already written — it always reformats from scratch. And it doesn't know about dialect-specific keywords like RETURNING (Postgres), MERGE (SQL Server), or UNNEST (BigQuery). For 90% of queries, it works. For the 10% it doesn't, the query was probably going to be hard to read anyway.

What this gets right: it's honest. It's a text formatter, not a parser. It doesn't pretend to understand your query. It knows what SQL looks like, and it makes the shape visible. That's all a formatter needs to do.

If you want to use this formatter in your own project, the function is above. Copy it, adapt it, extend it. The keyword list is where you'd add dialect-specific terms.

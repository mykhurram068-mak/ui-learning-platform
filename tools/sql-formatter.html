Why SQL formatting matters


Same query, same result — but one you can debug and one you can't.




SQL doesn't care about whitespace. The database engine parses the query, finds the keywords, and runs the logic. Indentation, line breaks, uppercase, color — none of it affects execution. A 400-character one-liner runs exactly as fast as a formatted, colored query with 15 lines.





The gap is for humans, not machines. When you're reading a query you wrote six months ago, or reviewing a colleague's pull request, or debugging why a report is returning wrong numbers, the formatted and colored version is what makes the difference.





A query on one line is unreadable past about 100 characters. A query with color but no formatting is still hard to scan — the colors tell you what each token is, but not what each clause does. The two together — structure and color — are what make a query readable at a glance.









How the formatter works


Two passes: format, then colorize. Each is small enough to read in a minute.




Pass 1 — format. The formatter normalizes whitespace, uppercases keywords, breaks on major clauses (SELECT, FROM, WHERE, JOIN, GROUP BY, ORDER BY, etc.), and indents AND/OR under their parent clause. Four regex passes, about 20 lines.





Pass 2 — colorize. The colorizer wraps each token in a `` with a class. Strings first (so keywords inside strings don't get colored). Then numbers, then functions, then keywords. About 30 lines.





The one critical line: escapeHtml runs before any tokenization. If someone pastes <script>alert(1)</script> as a SQL string, the escape function converts it to &lt;script&gt;... so it displays as literal text instead of running. This is the same escapeHtml function that's been in every build in the studio — the discipline doesn't change just because the output is now colored.





The Copy button reads from a hidden textarea. The visible output is HTML with spans; a second hidden field holds the plain text version. Copy always copies plain SQL, never markup. Same pattern as every code block in the studio — what you see is colored, what you copy is plain.









The five token types


Each color has a meaning. Once you know them, you can scan any query.








Keywords


SELECT · FROM · WHERE · JOIN · AND


The frame of the query. Where the eye should land first. Cyan matches the studio's accent color — the most important structure gets the most important color.







Functions


COUNT() · SUM() · COALESCE()


The transformations. Distinct from keywords — a function does something to data; a keyword organizes the query. Pink separates them without competing with cyan.







Strings


'paid' · 'pending' · 'active'


The literal values. Green — the same green used for "success" everywhere in the studio. A string is a value you can grep for in the DB.







Numbers


10 · 20.50 · 100


The literal quantities and thresholds. Amber draws the eye without shouting. When a query filters on a number, the number should stand out — that's the thing to double-check.







Identifiers and aliases


p.name · products · p · s


The content. Default text color for identifiers, muted italic for aliases. These should recede behind the structure — they're what the query is about, but the query's shape is what you're reviewing.









Why these five, not seven or ten: more colors is more visual noise, not more clarity. Five roles cover everything in a typical query. Comments (rare in pasted queries) would be a sixth, but this formatter doesn't currently colorize them — the token list is small on purpose.

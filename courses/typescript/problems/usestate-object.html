How to type useState with an object.
Nullable, partial, and correct.

useState({ name: 'Alice' }) works — inference handles it. But useState(null) doesn't, because TypeScript infers null, not User | null. And updating a single field of an object state requires a spread pattern that trips up beginners. This page covers both: the generic annotation for nullable state, and the correct update pattern for object state.

Short answer: Annotate with the generic when the initial value doesn't cover the full range: useState(null). Update with the functional setter and spread: setUser(prev => ({ ...prev, name: 'Bob' })). Never mutate the object directly — React compares state by reference and won't re-render.

✅ Solution 1 — Generic annotation for nullable state

When the object arrives later (fetch, form fill, selection).

The most common React + TS error: useState(null) infers the type null — nothing else. setUser(user) fails because User isn't assignable to null. Fix: provide the type explicitly. The generic argument expands the state's allowed range.

Inference from initial value

useState(null) → null. useState(0) → number. useState('') → string. The generic only when you need to widen.

The union annotation

useState(null) — the state can hold a User or null. setUser(user) and setUser(null) both compile.

Narrow before access

user is User | null. Accessing user.name requires narrowing: early return, optional chaining, or a check.

Same pattern for arrays

useState([]) — empty array annotation is required, because useState([]) infers never[].

✅ Solution 2 — Update a single field with spread

The pattern that trips up every React beginner.

Setting object state isn't like setting a primitive. React compares state by reference — mutating the existing object doesn't change the reference, so no re-render. The fix: always return a new object. Use the functional setter with spread: setUser(prev => ({ ...prev, name: 'Bob' })).

update-field.tsx 
import { useState } from 'react';

interface Form {
name: string;
email: string;
age: number;
}

function Form() {
const [form, setForm] = useState
({
name: '',
email: '',
age: 0
});

// ─── The bug: mutation doesn't re-render ─────
function badUpdate() {
form.name = 'Alice'; // ❌ mutates — React won't re-render
setForm(form); // same reference → bail out
}

// ─── The fix 1: spread (simple) ──────────────
function updateName(name: string) {
setForm({ ...form, name }); // ✅ new object
}

// ─── The fix 2: functional setter (safest) ───
function updateAge(age: number) {
setForm(prev => ({ ...prev, age })); // ✅ uses latest state
}

// ─── Why functional setter is better ─────────
// If two updates happen in the same tick:
// updateName('X') (closure captures old form)
// updateAge(30) (closure captures old form)
// Both spread from the same stale form — one update is lost.
//
// With functional setter:
// setForm(prev => ({ ...prev, name: 'X' }))
// setForm(prev => ({ ...prev, age: 30 }))
// Each receives the LATEST state — no lost update.

// ─── Nested object update ────────────────────

Never mutate

form.name = 'X' mutates the object. React compares state by reference — same reference, no re-render. Fix: always spread into a new object.

Functional setter

setForm(prev => ({ ...prev, name })) uses the latest state. Critical when two updates happen in the same tick — otherwise one is lost.

Spread at every level

Nested updates need spreads at every level: { ...prev, address: { ...prev.address, city } }. Each level creates a new object.

Why not Object.assign?

;

Object.assign(form, { name }) mutates — same problem as form.name = 'X'. Always return a new object.

The functional setter should be your default, not the exception. setUser(prev => ({ ...prev, name })) is one extra character than setUser({ ...user, name }) but it's always correct. The direct-spread form reads user from the closure — if two updates happen in the same render tick, both see stale state and one is lost. This bug is subtle, hard to reproduce, and shows up in production. Use the functional setter everywhere. You'll never debug a lost update again.

✅ Solution 3 — Typed setter helpers

Reusable, typed field updaters for object state.

If you have many fields, writing one spread-call per field gets repetitive. A typed helper generates the setter for any field: updateField('name', value). This is the pattern React Hook Form and similar libraries use internally — and it composes cleanly with TypeScript.

⚠️ Common mistakes

The useState-with-object bugs that cost real time.

1. Forgetting the generic on useState(null)

useState(null) infers null. setUser(user) fails. Fix: useState(null).

2. Mutating state directly

form.name = 'X' doesn't trigger a re-render — React compares by reference. Fix: always return a new object from the setter.

3. Using the direct-spread form in async code

setForm({ ...form, name }) captures stale form if called twice in the same tick. Fix: setForm(prev => ({ ...prev, name })).

4. Forgetting to spread nested levels

{ ...prev, address: { city } } drops zip. Fix: { ...prev, address: { ...prev.address, city } }.

5. Using Object.assign

Object.assign(form, { name }) mutates. Same bug as direct mutation. Fix: { ...form, name } or functional setter.

6. Not annotating empty arrays

useState([]) infers never[]. Fix: useState([]). Same pattern as nullable objects — annotate when inference isn't enough.

7. Using object state for related fields

Three useState calls that always change together are a smell. Fix: one useState with an object, or useReducer if transitions matter.

8. Accessing nullable state without narrowing

user.name when user is User | null fails. Fix: user?.name, early return, or explicit check.

❓ Frequently asked

How do I type useState with an object in TypeScript?

Provide the type as a generic argument to useState: const [user, setUser] = useState({ id: '1', name: 'Alice' }). If the state starts as null and the object comes later, use a union: useState(null). The generic is what tells TypeScript the full range of values the state can hold.

How do I update a single field of an object in useState?

Use the functional setter with spread: setUser(prev => ({ ...prev, name: 'Bob' })). The spread copies all fields, then 'name' overwrites one. This is required for correctness — mutating prev.name directly doesn't trigger a re-render. Always return a new object from the setter.

Why does useState(null) fail to accept setUser(user)?

Because TypeScript infers the state type from the initial value. useState(null) gives type null — not User | null. Calling setUser(user) then fails because User isn't assignable to null. Fix: provide the generic explicitly: useState(null).

Should I use useState or useReducer for object state?

Use useState if the object is simple and updates are independent. Use useReducer if the object has related fields that must transition together, or if the update logic is complex. Rule of thumb: 1–2 fields with simple updates → useState. 3+ related fields, or transitions → useReducer.

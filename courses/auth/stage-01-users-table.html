Stage 01 · 1.5–2 hours

Make a working login.
Users, session, the door.

Stage 01 builds a working login. A users table. A register form. A login form. A logout route. A session cookie. A @login_required decorator. Everything works. And every password is stored in plaintext — the worst possible thing to ship, and the whole point of starting here. You cannot appreciate the fix in Stage 02 until you've felt the problem.

1.5–2 hours Beginner Python · Flask · SQLite
Auth hub The users table Register Login The session The guard Why this is wrong Next: Stage 02

Short answer: A users table with id, email, password, created_at. A /register route that inserts a user, with the password stored in plaintext. A /login route that queries by email and compares the password with ==. On match, session['user_id'] = row['id']. A /logout route that calls session.clear(). A @login_required decorator that checks 'user_id' in session before the wrapped route runs. A secret key for the session to be signed. That's a complete login flow. It's also broken.

The users table

One table. Three columns that matter.

Every login system starts here. The table is the simplest part. Three columns carry the whole design: id, email, password. The id is internal — the session will store it. The email is how the user identifies themselves. The password is what proves they're who they claim.

schema.sql auth-stage-01.html · lines 12–19 
CREATE TABLE users (
id INTEGER PRIMARY KEY AUTOINCREMENT,
email TEXT NOT NULL UNIQUE,
password TEXT NOT NULL,
created_at TEXT NOT NULL
);
Why email is UNIQUE:

The email is the identifier. Two users
can't share an email - the login query
would have to pick one, and it has no
way to know which.

The UNIQUE constraint enforces the rule
at the schema level. A duplicate insert
fails with a clear error. The register
route also checks before inserting (for
a nicer message), but the schema is the
safety net.

Why the column is named 'password' and
not 'password_hash':

Because in Stage 01 it stores a plaintext
password. Naming it 'password_hash' would
be dishonest - the column would lie about
its contents.

In Stage 02, when hashing is introduced,
the column gets renamed to 'password_hash'.
That rename is visible in the code and in
the schema. It's a signal: what's stored
here is not the password, it's a hash.

Naming honesty is a discipline. Columns
should describe what they actually contain.

Why there's no 'active' or 'role' column yet:

Stage 01 is the minimum for a working
login. Roles come in Stage 03. An active
flag (to soft-delete users) isn't in the
scope of this course.

Adding columns later is easy. Removing
them is not. Start with the minimum,
add as the design demands.

Four columns. That's the whole table. Every auth system in every framework is built on this shape — an internal ID, an identifier the user provides, and something only the user knows. Django, Rails, Express — the table looks like this in all of them. The names and types vary; the structure doesn't.

Register — a new user, a new row

POST a form, insert a row.

The register route reads the submitted email and password, checks whether the email is already taken, and if not, inserts a new row. Three lines of substance. The rest is validation and error handling.

register.py auth-stage-01.html · lines 45–60 
@app.route("/register", methods=["POST"])
def register():
email = request.form["email"].strip().lower()
password = request.form["password"]

with get_db() as conn:
existing = conn.execute(
"SELECT id FROM users WHERE email = ?", (email,)
).fetchone()
if existing:
return render_template("register.html", error="Email already registered."), 400

conn.execute(
"INSERT INTO users (email, password, created_at) VALUES (?, ?, ?)",
(email, password, now_iso()),
)
conn.commit()

return redirect("/login")
Why the error is 'Invalid email or password'
and not 'Wrong password':

Because telling the user which part failed
is a security leak. An attacker can use
'Wrong password' to enumerate valid emails
• try 1000 emails, see which ones say
'Wrong password' vs 'No such user', and
now you know 500 valid emails to focus
on.

'Invalid email or password' is ambiguous
on purpose. The legitimate user knows
which they typed wrong; an attacker
learns nothing.

This is a small discipline that costs
nothing and closes a real hole. Same
pattern as every auth system that's been
audited.

Why 401 not 400:

400 = bad request. The client sent
something malformed - missing field,
bad JSON.
401 = unauthorized. The request was
well-formed, but the credentials are
wrong.

Login with wrong password is 401, not
400. The request is valid; the identity
is not. The distinction matters for
clients and for readability.

Why session['user_id'] = user['id']:

This is the whole point of login. Set
the user's ID in the session. From now
on, every request from this browser
carries that session, and the server
can read user_id from it.

The value stored is the id, not the email
or the whole user row. The id is the
smallest identifier that uniquely points
to the user. Look up the rest (email,
role) from the database when needed.

Storing the whole user row in the session
would mean stale data after any profile
update. Storing the id means the session
points to the current state, always.

Why no password check length or complexity:

Stage 01's login doesn't validate input
beyond what's needed for the flow. Real
production apps check minimum length,
complexity, and (in some jurisdictions)
dictionary checks. Those are policies,
not patterns. They belong in a product's
requirements, not a course on auth.

The pattern here is: query by identifier,
compare the secret, set the session.
That's what login is.

The session — a cookie the browser carries

One line to set. One line to read. One line to clear.

The session is Flask's built-in cookie-based session. You set session['user_id'], Flask signs it with a secret key and sends it as a cookie, and every subsequent request has session['user_id'] available. The three operations you need: set, read, clear.

session.py auth-stage-01.html · lines 105–125 
import os
from flask import session

app.secret_key = os.environ.get("SECRET_KEY", os.urandom(24))

@app.route("/logout")
def logout():
session.clear()
return redirect("/login")

@app.route("/dashboard")
def dashboard():
if "user_id" not in session:
return redirect("/login")
return render_template("dashboard.html", user_id=session["user_id"])
Why the secret key must be persistent:

Flask signs the session cookie with the
secret key. If the key changes, all
existing sessions become invalid - every
user gets logged out.

os.urandom(24) generates a random key
every time the app starts. That means
every restart logs everyone out. Fine
for a course demo, wrong for production.

In production, set SECRET_KEY as an
environment variable and never change it.
The value should be random and long
(32+ bytes). Anyone who knows the key
can forge sessions - treat it like a
password.

Why session.clear() and not just deleting
user_id:

session.clear() removes everything in
the session - user_id, and anything else
that gets added later (roles, preferences).
The user is logged out completely.

del session['user_id'] would only remove
that one key. If the app later stores
other session data, logout would leave
it behind. session.clear() is the honest
reset.

Same reasoning as 'delete the whole row'
vs 'delete one column' - if the goal is
a clean slate, clear the slate.

Why Flask's default session is client-side:

Flask's built-in session stores the data
in the cookie itself, base64-encoded and
signed. The server doesn't hold a session
store. When a request comes in, Flask
reads the cookie, verifies the signature,
and reconstructs the session dict.

This means:
- The data is visible to the user
(base64, not encrypted).
- The data can't be tampered with
(the signature protects it).
- The server doesn't need a session
store, so it scales horizontally
with no sticky sessions.

For a course, this is exactly the right
default. For production, if you need
server-side sessions (say, to revoke a
session immediately), Flask-Session is
the extension. That's a one-paragraph
detour, not a course.

Why the dashboard checks session manually
here:

Because Stage 01 introduces the concept
before the decorator. The next snippet
shows the @login_required decorator
that wraps this check so every protected
route doesn't have to repeat it.

The manual check is the raw pattern.
The decorator is the pattern factored
out. Understanding both is understanding
what decorators are for.

The guard — @login_required

A decorator is a function that wraps a function.

The manual if "user_id" not in session check works, but you'd have to paste it into every protected route. The @login_required decorator factors it out. Write it once, apply it to every route that needs protection.

guard.py auth-stage-01.html · lines 140–155 
from functools import wraps

def login_required(f):
@wraps(f)
def wrapper(*args, **kwargs):
if "user_id" not in session:
return redirect("/login")
return f(*args, **kwargs)
return wrapper

@app.route("/dashboard")
@login_required
def dashboard():
return render_template("dashboard.html", user_id=session["user_id"])
What a decorator actually is:

@login_required above def dashboard is
exactly equivalent to:
dashboard = login_required(dashboard)

login_required takes a function, returns
a new function (wrapper), and the new
function is what gets called when /dashboard
is requested.

The wrapper checks the session first. If
logged in, it calls the original function.
If not, it returns a redirect - the original
function never runs.

This is 'before this route runs, check
something.' Every authentication and
authorization pattern is a variant of
this idea.

Why @wraps(f) matters:

Without @wraps, the wrapper function would
be named 'wrapper' and lose the original
function's name, docstring, and metadata.
Flask uses these to register the route -
losing them breaks routing.

@wraps(f) copies them over. The wrapper
looks like the original from the outside.

This is a footgun. Forgetting @wraps is a
common bug that produces confusing error
messages ('wrapper has no attribute ...').
Remember it every time.

Why *args and **kwargs:

The wrapper doesn't know the original
function's parameters. Some routes take
path parameters (@app.route('/user/')),
some don't. The wrapper forwards whatever
it receives.

*args collects positional arguments,
**kwargs collects keyword arguments.
Together they forward everything the
route was called with.

This is standard decorator plumbing.
Once you know it, it's invisible.

The order of decorators:

@app.route("/dashboard")
@login_required
def dashboard():
...

@app.route is applied first (bottom
decorator runs first), so Flask registers
the login_required-wrapped version.

If you flip them:
@login_required
@app.route("/dashboard")
...Flask would try to register login_required
as the route handler, which doesn't work.

Order matters. @app.route always goes on
top.

Why the guard is on every route, not just
the dashboard:

Authentication is per-request. Every
protected route needs the guard. Pasting
the check in every route function works,
but it's easy to forget one - and forgetting
is a security hole, not a bug.

The decorator makes the check visible at
the route definition. Missing it is
obvious in code review. Same reasoning as
@role_required in Stage 03 - the check
lives where the route lives.

Why this is wrong — and what comes next

It works. It's also the worst thing to ship.

Everything in this stage works. You can register, log in, see a protected page, and log out. So why is it wrong?

The leak

If the database is ever exposed — a backup leak, a SQL injection, a stolen laptop — every user's password is in the clear. Not "encrypted, but breakable with effort." Plaintext. Right there in a column called password.

The reuse problem

People reuse passwords. The same password on your app and on their email, their bank, their social media. A leak of your database becomes a credential-stuffing attack against everywhere else they've signed up.

The insider problem

Anyone with database access — a contractor, a curious employee, an attacker who got read-only access — can see every password without doing anything clever. The data is right there in a SELECT *.

The support problem

Users forget passwords. They email you asking for help. If you store plaintext, you can read their password and tell them. That feels helpful. It also means you now know their password. It's a privacy violation dressed as a feature.

The fix is one idea: don't store the password. Store a hash of the password. A hash is a one-way function. Feed it the password, get back a fixed-length string. You can't reverse it. To check a login, hash the submitted password and compare the hashes. If someone steals the database, they get a bunch of random-looking strings that can't be turned back into passwords.

Stage 02 changes exactly two lines. The INSERT in /register becomes generate_password_hash(password). The comparison in /login becomes check_password_hash(user["password_hash"], password). The table renames its password column to password_hash. The session, the guard, the routes — all identical.

That's why Stage 01 exists. So that when Stage 02 changes two lines, you understand exactly what changed, why, and what would have happened if you hadn't.

Next: Stage 02 — Hashing & Sessions

The fix, made small and obvious.

Stage 02 replaces plaintext with a hash. The change is small on purpose — the whole point is that the security of the system doesn't come from a big rewrite, it comes from one small, correct choice applied in two places.

The four big lessons in Stage 02:

  • Hashing vs encryption — one-way vs two-way. Why passwords must be hashed, never encrypted.
  • Salts — why the same password produces different hashes for different users. Why a rainbow table stops working.
  • generate_password_hash and check_password_hash — the two werkzeug functions that do the work.
  • The migration — what happens to existing users when the column changes. (Spoiler: we reset their passwords, because there's no way to hash a plaintext password without knowing it, and we shouldn't know it. That's a real-world conversation, handled honestly.)

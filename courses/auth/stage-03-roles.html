Stage 03 · 1.5–2 hours

Who are you is done.
Now: what can you do?

Authentication says who. Authorization says what. Stages 01 and 02 completed authentication — the app knows who's making a request, and the passwords are hashed. Stage 03 adds authorization: a role column, a @role_required decorator, and the three roles every app starts with — viewer, editor, admin. The code is small. The bug that appears when you forget the decorator is not.

Short answer: Add a role column to users with a CHECK constraint (viewer, editor, admin). Write a @role_required(*roles) decorator that reads session["user_id"], looks up the user's role from the DB, and returns 403 if the role isn't in the allowed list. Layer it with @login_required on every protected route — or make @role_required imply @login_required so you can't forget the login check. The lesson shows both, and explains why the second is safer.

Authentication vs authorization

Two questions. Two layers. Confusing them is a security bug.

The two words look similar and get conflated constantly. They answer different questions and happen at different times. Getting the distinction right is most of what this stage teaches.

Authentication

Who are you? Happens once, at login. Succeeds when the password hash matches. Produces a session. Every request after that carries the session.

Authorization

What can you do? Happens on every request. Succeeds when the user's role permits the action. Fails with 403 Forbidden.

The wrong mental model

"Logged in = allowed." No. Logged in means the app knows who you are. It doesn't mean you can delete every user. Authz is a separate check.

The correct mental model

Every protected action has two gates. Gate 1: are you logged in? Gate 2: does your role permit this? Both must pass. Skipping gate 2 is the bug this stage prevents.

A concrete example. A viewer logs in. Gate 1 (authentication) passes — they're logged in. Now they navigate to "DELETE /users/42", a route that only admins should reach. If the route has only @login_required, the request goes through. The viewer just deleted the admin. That's the forgotten-decorator bug, and it's the reason this stage exists.

The rule that prevents it: every route that touches sensitive data must check both authentication and authorization. The first says "you're someone." The second says "you're the right someone." Both are required. Neither is sufficient alone.

The role column

One column. Three values. A CHECK constraint.

The users table gains one column. role is a TEXT column with three allowed values. The CHECK constraint is the schema-level enforcement: no code path can insert a role that isn't in the list, no matter what.

schema.sql auth-stage-03.html · lines 12–20 
CREATE TABLE users (
id INTEGER PRIMARY KEY AUTOINCREMENT,
email TEXT NOT NULL UNIQUE,
password_hash TEXT NOT NULL,
role TEXT NOT NULL DEFAULT 'viewer'
CHECK (role IN ('viewer', 'editor', 'admin')),
created_at TEXT NOT NULL
);
Why DEFAULT 'viewer':

New users should have the minimum
permissions. A user who just registered
hasn't been vetted, hasn't been promoted,
hasn't been assigned any responsibilities.

Default to the safest role. Admins are
made explicitly - by another admin - not
by default.

This is the principle of least privilege:
every user starts with the minimum needed
to use the app, and gets more only when
someone grants it.

Why the CHECK constraint:

Without it, a buggy code path could insert
role='superadmin' or role='Admin' or an
empty string. The CHECK constraint refuses
all of them - the database itself enforces
the three-value enum.

This is defense in depth. The decorator
also checks the role against an allowed
list at request time. But if the decorator
has a bug, or a new role gets added to the
DB without updating the decorator, the DB
catches it first.

Same pattern as every CHECK in the
studio's builds: state is enforced at the
schema, so bad data can't get in.

Why three roles, not five or ten:

The user said 'for most apps, RBAC with
three or four roles is enough.' This is
that claim made concrete.

viewer - can read, can't modify
editor - can read and modify
admin - can do everything, including
delete and manage users

That's the standard trio. If your app
has 'manager' or 'moderator', it's usually
a viewer or editor with a specific scope,
not a fundamentally different role.

Start with three. Add a fourth only when
the access patterns genuinely demand it.
The lesson names this so you know the
default is not an accident.

Why role and not permissions:

A permissions table would look like:
user_permissions(user_id, permission)
- alice -> 'delete_user'
- alice -> 'edit_user'
- bob -> 'edit_user'

That's more flexible. Each user has an
arbitrary set of permissions. You could
have a user who can delete but not edit,
or edit but not delete.

It's also more code. Every check has to
look up the user's permissions. Every
'can this user do X?' has to be a query.
Every UI that hides buttons has to ask
the server 'what can I do?'

RBAC with three roles is simpler and
covers 90% of apps. The lesson is: pick
the simplest tool that fits, not the most
flexible tool that might be needed later.

The @role_required decorator

Same pattern as @login_required. Different check.

The @role_required decorator reads the user's role from the database using session["user_id"], checks whether it's in the allowed list, and either calls the route or returns 403 Forbidden. The lookup on every request is deliberate — see the "Why" tab.

role_required.py auth-stage-03.html · lines 35–55 
from functools import wraps

def role_required(*allowed_roles):
def decorator(f):
@wraps(f)
def wrapper(*args, **kwargs):
if "user_id" not in session:
return redirect("/login")
with get_db() as conn:
user = conn.execute(
"SELECT role FROM users WHERE id = ?", (session["user_id"],)
).fetchone()
if not user or user["role"] not in allowed_roles:
return "Forbidden", 403
return f(*args, **kwargs)
return wrapper
return decorator
Why @role_required takes arguments:

@login_required doesn't take arguments -
it just checks 'is anyone logged in?'

@role_required needs to know which roles
are allowed. That's an argument:
@role_required("admin")
@role_required("editor", "admin")

A decorator that takes arguments returns
a decorator. Three levels:
role_required(*roles) returns a function
that takes f and returns wrapper

This is the standard pattern for
parameterized decorators. The extra level
is the argument-capture level.

Why the DB lookup on every request:

The role lives in the database. If you
put it in the session at login, the role
is a snapshot - stale if it changes. If
you look it up on every request, the role
is current.

For a course, correctness matters more
than the query cost. One SELECT per
protected request is fine for any app
that isn't handling thousands of requests
per second.

The trade-off: if you had a hot route
that admins hit constantly, you'd cache
the role in session with a short TTL.
The lesson names this so you know when
to switch. Stage 03 uses the DB lookup
because it's simpler and always correct.

Why 403 not 404:

404 means 'not found'. The route exists;
the user just can't access it. Returning
404 would be lying to the client.

403 means 'Forbidden'. The client is
authenticated (not 401) and the server
refuses to run the request. That's
exactly what's happening.

Some apps use 404 for authorization
failures as a security-by-obscurity
measure - don't reveal that the route
exists. That's a valid choice for some
apps (e.g., a user endpoint whose existence
is sensitive). For a course, 403 is the
honest default.

Why 'not user' is checked:

If session['user_id'] points to a user
that was deleted between login and this
request, the SELECT returns None. The
wrapper returns 403, which is correct -
the user is effectively no longer a user.

This is an edge case, but it's real: an
admin deletes a user, the user's session
is still active, they navigate to a
protected route. Without 'not user', the
code would crash on user['role']. With
it, the request is denied cleanly.

Why the decorator is three functions,
not one:

role_required(*allowed_roles) - captures
the role arguments. Returns decorator.

decorator(f) - receives the route function.
Returns wrapper.

wrapper(*args, **kwargs) - runs per
request. Checks the role. Calls f or
returns 403.

Each level is necessary for the
parameterized decorator pattern. There's
no way to do it in fewer functions and
keep the arguments.

Layering decorators

Or: why @role_required should imply @login_required.

Two ways to apply the decorators. The first is explicit: put both on the route. The second is safer: make @role_required do the login check itself, so you can't forget.

usage.py auth-stage-03.html · lines 70–90 
@app.route("/admin/delete/", methods=["POST"])
@login_required
@role_required("admin")
def delete_user(user_id):
with get_db() as conn:
conn.execute("DELETE FROM users WHERE id = ?", (user_id,))
conn.commit()
return redirect("/admin/users")

@app.route("/editor/posts/new", methods=["GET"])
@login_required
@role_required("editor", "admin")
def new_post():
return render_template("new_post.html")
The order of decorators matters:

@app.route - always on top
@login_required - first
@role_required - second
def route...

Decorators are applied bottom-up.
role_required wraps the function first,
then login_required wraps that, then
app.route registers the whole thing.

At request time, the order is top-down:
app.route's handler calls login_required's
wrapper, which calls role_required's
wrapper, which calls the actual function.

Both checks run, but login runs first.
If not logged in, redirect to login.
If logged in but wrong role, 403.

Why @role_required checks login internally:

Notice in the decorator code that even
though @login_required runs first,
@role_required also has:
if "user_id" not in session:
return redirect("/login")

That's intentional. It makes
@role_required safe on its own - if a
future route forgets @login_required,
@role_required still catches the
unauthenticated case.

The cost is a tiny bit of redundancy
(one extra 'in session' check per
request). The benefit is that a single
forgotten decorator doesn't open a
security hole.

This is defensive design. The check
that matters (are you an admin?) runs
regardless of the check that precedes it.

Why you might also want @login_required
alongside @role_required:

With the internal check, @role_required
alone would work. Adding @login_required
is belt and suspenders - it makes the
intent visible ('this route requires
login AND requires a role').

Some code styles prefer explicit. Some
prefer minimal. Both are correct if
@role_required is safe on its own.

The lesson shows both: the explicit
version (@login_required + @role_required)
as the default, and the safe-alone
version (role_required internally
checks login) as the safety net.

The bug that this design prevents:

Consider a route:
@app.route("/admin/users")
@role_required("admin")
def admin_users():
return render_template("admin_users.html")

If @role_required didn't check login,
and a future developer copied this route
but removed @login_required (thinking it
was redundant), the route would still
work for logged-in admins - and would
crash for unauthenticated users (user_id
not in session -> KeyError in the query).

With the internal check, the crash
becomes a redirect to login. The route
is safe regardless of the surrounding
decorators.

This is why the internal check is worth
the tiny redundancy.

The forgotten decorator

The most common authorization bug. Shown, so you recognize it.

Here's the bug, in its natural habitat. A developer writes a delete route. They remember to check login. They forget to check role. Every logged-in user can now delete every other user. 

# BROKEN - @login_required only
@app.route("/admin/delete/", methods=["POST"])
@login_required
def delete_user(user_id):
conn.execute("DELETE FROM users WHERE id = ?", (user_id,))
conn.commit()
return redirect("/admin/users")

A viewer logs in. Their session is valid. @login_required passes.
The DELETE runs. The viewer just deleted the admin.
Nothing in the code prevents this.

FIXED - both decorators
@app.route("/admin/delete/", methods=["POST"])
@login_required
@role_required("admin")
def delete_user(user_id):
conn.execute("DELETE FROM users WHERE id = ?", (user_id,))
conn.commit()
return redirect("/admin/users")

A viewer logs in. @login_required passes. @role_required returns 403.
The DELETE does not run.

Why this bug is so common: because "logged in" feels like "authorized." For the vast majority of routes in a small app, logged-in is the right check — anyone logged in can see their own dashboard, edit their own profile, view their own settings. The @login_required decorator becomes muscle memory. Then a route comes along that needs more, and the developer writes the decorator they always write.

The fix that prevents it structurally: make @role_required imply @login_required. If a route requires a role, it can't accidentally be reachable by someone who's not logged in — the decorator checks both. And a route that requires a role is by definition a route where "logged in" is not enough, so the two checks belong together.

The discipline: every route that can modify other users' data, change permissions, delete records, or see data the user doesn't own needs a @role_required. Not just @login_required. The question to ask is never "are they logged in?" but "are they allowed?".

Next: Stage 04 — Applied to HR

Everything you've learned, in a real app.

Stages 01–03 built auth in a vacuum. A small demo app with a login page and a dashboard. Stage 04 takes that whole pattern and drops it into the HR & Attendance build — a real app, with real routes, where the change has visible consequences.

The four big lessons in Stage 04:

  • Adding a users table to an existing app. The HR build already has employees — how does users relate? (Spoiler: a user is an account; an employee is a person. Same person, different records. The employee_id foreign key is the connection.)
  • Adding login to an existing HTML. The HR build already has a manager view and an employee view. Login sits in front of both. Which view a user lands on depends on their role.
  • Protecting existing routes. The HR build already has /api/clock-in, /api/employees, /api/approve-week. Each needs the right decorator: some need @login_required, some need @role_required("manager").
  • What the app actually gains. Before: anyone with a browser could clock in as any employee, approve any timesheet, see any payroll data. After: the manager view is manager-only; the employee view is employee-only; the audit log shows who approved what, because "who" is now a real user.

Stage 04's full file is the HR build with auth integrated. It's the largest file in this course — about 350 lines of code changes across the existing HR files. The lesson page is still one stage, still ~550 lines, with 4–6 snippets and text-heavy explanation. The point isn't the code; the point is how a pattern from a demo becomes a real feature in a real app.

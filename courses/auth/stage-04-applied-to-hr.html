Stages 01–03 built auth in a vacuum. A small demo app with a login page and a dashboard. Users + employees — two tables, one person

A user is an account. An employee is a person. The FK connects them.

The HR build already has an employees table. It stores names, hourly rates, and hire dates — the facts about a person who works there. Stage 04 adds a users table on top of it. A user is an account: email, password hash, role, session. In the common case, one user corresponds to one employee, and the FK on the user points at the employee.

This separation matters because it's not always 1:1. An HR admin might have a user account (to log in and manage the app) but no employee record (because they don't clock in and don't get paid by the hour). An employee might have an employee record before they have a user account (a new hire who hasn't received their login email yet). The FK is nullable, and that's correct.

schema.sql (excerpt) auth-stage-04.html · lines 15–28 
CREATE TABLE users (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  email         TEXT NOT NULL UNIQUE,
  password_hash TEXT NOT NULL,
  role          TEXT NOT NULL DEFAULT 'employee'
                CHECK (role IN ('employee', 'manager')),
  employee_id   INTEGER,
  created_at    TEXT NOT NULL,
  FOREIGN KEY (employee_id) REFERENCES employees(id) ON DELETE SET NULL
);
Why two roles, not three:

  The HR build has two audiences: employees
  and managers. An employee clocks in and out.
  A manager does that plus approves timesheets.
  No third role is needed.

  In a bigger org you'd add 'hr_admin' for
  someone who manages the payroll data but
  isn't a manager themselves. The CHECK
  constraint has room for it - add a value
  to the IN list and a role to the decorator
  call. Stage 04 uses two because the app
  has two.

Why employee_id is nullable:

  Not every user is an employee. An IT admin
  might have a login to fix the app without
  ever clocking in. An employee's user account
  might be created before their employee
  record is (order-of-creation edge case).

  Nullable FK means either state is valid.
  The role check doesn't require employee_id.
  The role check requires a role.

Why ON DELETE SET NULL and not CASCADE:

  If an employee record is deleted, the user
  account should survive. The person still
  exists - they just don't work there anymore.
  Their login still works for the app, but
  they can't clock in because there's no
  employee record to attribute hours to.

  CASCADE would delete the user. That's too
  aggressive - you'd lose their login history,
  their audit trail, their session's identity
  in old logs.

  SET NULL is the correct default for
  'reference, but don't depend'.

Why role lives on users, not employees:

  The role describes the account, not the
  person. An employee could be an employee
  today and a manager tomorrow - that's an
  account role change, not an employee record
  change.

  Put it on users, next to the password and
  the session. The employee record stays
  about the person. The user record stays
  about the login.

The whole schema change is 10 lines. That's the pattern: a new table (users), one FK to the existing table (employee_id), one CHECK constraint on role. The HR build's existing four tables stay exactly the same. Auth is additive — it wraps the app, it doesn't rewrite it.

The login gate — one page in front of everything

Same login form. Same session. Same decorator. New app.

The HR build already has HTML routes (/, /dashboard, /employee, /manager) and API routes (/api/clock-in, /api/approve-week, etc.). Stage 04 adds one new HTML route — /login — and wraps every existing HTML route in @login_required. The gate sits in front of the app.

app.py (excerpt) auth-stage-04.html · lines 45–65 
@app.route("/")
@login_required
def index():
    """Serve the HR app. The role determines what the tab bar shows."""
    user = current_user()
    return render_template("app.html", user=user)

@app.route("/login", methods=["GET", "POST"])
def login():
    if request.method == "GET":
        return render_template("login.html")
    email = request.form["email"].strip().lower()
    password = request.form["password"]
    with get_db() as conn:
        user = conn.execute(
            "SELECT id, password_hash FROM users WHERE email = ?", (email,)
        ).fetchone()
    if not user or not check_password_hash(user["password_hash"], password):
        return render_template("login.html", error="Invalid email or password."), 401
    session["user_id"] = user["id"]
    return redirect("/")
Why the login route is a form POST,
not an API call:

  Two approaches work. (1) The form submits
  to /login, the server sets a session cookie,
  the browser is redirected to /. (2) JavaScript
  fetches /api/login, gets a token, stores it,
  sends it in headers. 

  Option 1 is simpler for a server-rendered
  app. The session cookie is set by the
  browser automatically. No JS involved.
  Login is a full page reload, but that's a
  one-time cost.

  Option 2 is necessary if the frontend is
  a separate app (React SPA, mobile client).
  Not our case.

  Stage 04 uses option 1. Same as the HR
  build's existing HTML routes - server-rendered,
  form-posted. Consistent with the app.

Why the login page is now the entry point:

  Before Stage 04, visiting / went straight
  to the HR dashboard. After Stage 04,
  visiting / without a session redirects to
  /login. The redirect is automatic because
  of @login_required.

  This is the "gate" pattern: the app is
  behind a check. The check is one decorator
  on one route. Everything else flows from
  there.

Why 'user' is passed to the template:

  The HR app's template needs to know the
  user's role, name, and employee_id to
  render the right tab bar, the right views,
  and the right data.

  Passing the full user row (id, email, role,
  employee_id) means the template has
  everything it needs in one object. No
  extra queries, no template-side lookups.

  The template uses {% if user['role'] ==
  'manager' %} to decide what to show. That's
  the UI-level check. The API-level check
  (next section) is the enforcement.

The whole gate is 20 lines of code. A login route that checks the password hash and sets the session. A decorator on the index route. The app's existing routes don't change — they just get the decorator added.

Role-aware UI — the tab bar changes

Hide what the user can't use. Show what they can.

The HR build already has a tab bar with two tabs: Manager and Employee. Before auth, both tabs were visible to everyone. After auth, the tab bar is role-aware: an employee sees only the Employee tab; a manager sees both. Same HTML, one template condition.

app.html (excerpt) auth-stage-04.html · lines 78–95 
<header class="hr-header">
  <div class="hr-brand">MAK HR</div>
  <div class="hr-tabs">
    {% if user['role'] == 'manager' %}
    <button class="hr-tab" data-switch="manager">Manager</button>
    {% endif %}
    <button class="hr-tab" data-switch="employee">Employee</button>
  </div>
  <div class="hr-user">
    {{ user['email'] }} · {{ user['role'] }}
    <a href="/logout">Log out</a>
  </div>
</header>
Why the manager tab is behind a condition:

  An employee should never see a tab they
  can't use. Clicking it would get a 403,
  which is confusing. Hiding it means the
  employee never tries.

  This is the UX half of authorization. The
  API half is the enforcement.

Why the employee tab isn't conditioned:

  Both roles can clock in and out. An employee
  clocks in; a manager can also clock in
  (managers are people who work shifts too,
  or at least might need to record hours for
  someone else).

  So the employee tab is visible to everyone.
  The manager tab is manager-only.

  The rule: hide what the user can't use.
  Show what they can. The Employee tab is
  always usable.

Why user info is in the header:

  The user needs to know who they're logged
  in as. The email + role in the header
  answers that in one glance. The logout
  link is right there.

  This is standard app UX. Every authenticated
  app shows the current user somewhere in
  the chrome. Stage 04 makes the HR build do
  the same.

Two lines of Jinja. The whole UI change. The {% if %} around the manager tab, and the user info block in the header. The rest of the HR app's HTML is unchanged. Role-aware UI is small on purpose.

API protection — the enforcement boundary

The UI hides buttons. The API refuses requests. Both matter. The API is the one that counts.

The HR build has API routes for clock-in, clock-out, break, and approve-week. Before auth, any of them could be called by anyone. After auth, each one has the right decorator: @login_required for clock actions (any logged-in user), @role_required("manager") for approve-week (managers only).

app.py (API routes) auth-stage-04.html · lines 110–135 
@app.route("/api/clock-in", methods=["POST"])
@login_required
def clock_in():
    """Any logged-in user can clock in for themselves."""
    user = current_user()
    if not user["employee_id"]:
        return jsonify({"error": "No employee record for this account."}), 400
    # ... existing clock-in logic, using user["employee_id"] ...

@app.route("/api/approve-week", methods=["POST"])
@role_required("manager")
def approve_week():
    """Only managers can approve timesheets."""
    # ... existing approve-week logic ...
    return jsonify({"ok": True}), 200
Why clock-in uses employee_id, not a request field:

  Before auth, the frontend sent {"employeeId":
  5} in the POST body. The server trusted it.
  Anyone could clock in as anyone by sending
  a different employeeId.

  After auth, the server doesn't trust the
  body. It uses user["employee_id"] - the
  employee associated with the logged-in
  user. The employeeId in the body is ignored
  (or removed entirely).

  This is the same discipline as every write
  in the studio's builds: never trust the
  client with identity. The session is the
  identity. The body is a payload.

Why approve-week needs role_required, not
just login_required:

  Any employee could approve their own
  timesheet if only login_required were on
  the route. The role check is what makes
  'approve' mean 'a manager approved it'.

  Same forgotten-decorator bug from Stage 03:
  login_required checks that you're someone,
  not that you're the right someone. Approve
  is the right-someone case.

  Same for delete-user, if the HR app had
  one. Admin actions need admin roles.

Why the API returns 403 and not a redirect:

  The HTML routes redirect to /login on 401
  because the user is navigating. A page
  reload to login is fine.

  The API returns 403 (or 401) as JSON,
  because the client is a JavaScript fetch.
  A redirect would confuse the fetch handler
  - the client expects JSON, gets HTML.

  The client handles 401/403 by showing a
  toast and (for 401) redirecting to login
  via window.location. That's the client's
  job. The server just tells the truth in
  the response.

The API protection is the enforcement boundary. The UI can hide the approve button for employees, but a determined employee with DevTools can still POST to /api/approve-week. The @role_required("manager") decorator is what actually stops them. UI-level hiding is UX. API-level checking is security. Both matter. The API is the one that holds under attack.

The audit log — who, not just what

Every event is now attributed to a user.

The HR build already has an attendance_events table. It records every clock-in, clock-out, and break, with a timestamp. But before auth, the log said what happened, not who caused it. Stage 04 adds a user_id column to the events table, so the audit log can answer both.

schema.sql (addition) auth-stage-04.html · lines 145–155 
CREATE TABLE attendance_events (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  employee_id INTEGER NOT NULL,
  type        TEXT NOT NULL
              CHECK (type IN ('in', 'out', 'break_start', 'break_end',
                              'manual_in', 'manual_out')),
  occurred_at TEXT NOT NULL,
  note        TEXT,
  created_by  INTEGER,
  created_at  TEXT NOT NULL,
  FOREIGN KEY (employee_id) REFERENCES employees(id) ON DELETE RESTRICT,
  FOREIGN KEY (created_by)  REFERENCES users(id)     ON DELETE SET NULL
);
Why both employee_id and created_by:

  Two different questions:
    employee_id  - whose hours is this?
    created_by   - who recorded this event?

  In the common case, they're the same person:
  Alice clocks in for herself, employee_id =
  Alice's employee record, created_by = Alice's
  user account.

  But they're not always the same. A manager
  might correct a missed clock-out for an
  employee who forgot. Then:
    employee_id = the employee
    created_by  = the manager

  The audit log now shows 'Alice's clock-out
  was recorded by manager Bob at 10:05 AM.'
  That's the sentence a payroll audit needs.

Why created_by is nullable:

  Events created before auth existed have no
  created_by. That's fine - they predate the
  feature, and forcing a value would mean
  inventing a user, which is worse.

  New events always have created_by set
  (because all writes go through an
  authenticated endpoint). Old events have
  NULL, and the log renders them as 'system'
  or 'pre-auth'.

  Same pattern as the delivery_events
  created_by field in the Delivery Tracking
  build. Audit fields are best added before
  you need them, but nullable is the honest
  migration for an existing table.

Why ON DELETE SET NULL and not CASCADE:

  If a user account is deleted, the events
  they created should survive. The audit log
  is a historical record. Deleting a user
  shouldn't erase their history.

  SET NULL means the created_by column
  becomes NULL if the user is deleted. The
  event survives with 'system' or 'deleted
  user' as the attribution.

  CASCADE would delete the events. That's
  wrong. History doesn't get deleted when
  a person leaves - it becomes historical.

What the audit log now answers:

  Before Stage 04:
    'Someone approved week 44.' (who?)
    'Someone clocked in at 9:02.' (whose?)

  After Stage 04:
    'Manager Bob (bob@example.com) approved
    week 44 at 10:05 AM.'
    'Alice clocked in at 9:02. Recorded by
    Alice.'
    'Alice's clock-out was manually corrected
    by manager Bob at 10:05 AM.'

  Every sentence is now auditable. Every
  action has a who.

This is what auth enables that nothing else does: attribution. Before auth, the HR build could tell you what happened. After auth, it can tell you who. That's the difference between an app and an audit trail. Any action taken by an authenticated user should record created_by. Every write should attribute itself.

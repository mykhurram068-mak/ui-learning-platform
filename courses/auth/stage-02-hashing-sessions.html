Stage 02 · 1.5–2 hours

The fix.
Two lines. One column. Same door.

Stage 01 gave you a working login. Stage 02 makes it safe. That's it. Two lines in app.py change. One column in the schema renames. The session, the guard, the routes, the templates — all identical. The point of splitting them was to show that making a login safe is a small change to a working shape, not a rewrite. That distinction matters, because "rewrite the auth system" is a scary sentence and "change two lines" is not.

Short answer: Rename the column password to password_hash. In /register, replace password with generate_password_hash(password). In /login, replace user["password"] != password with not check_password_hash(user["password_hash"], password). Import both functions from werkzeug.security. That's the whole change. Same session, same @login_required, same routes. The lock changed; the door didn't.

What changes — and what doesn't

The shape stays. The storage changes.

This is the most important thing to understand before reading the code: almost nothing changes. The login flow is the same. The session is set the same. The decorator guards the same routes. The templates render the same. Only the storage of the password changes — what goes into the database column, and how the login route compares the submitted password against it.

Changes

The users.password column renames to password_hash. The value stored is a hash, not the password. The comparison in /login uses check_password_hash, not ==.

Does not change

The users table's other columns. The register flow. The login flow's shape. The session mechanism. The @login_required decorator. The dashboard. The logout route.

Why this is the right shape

Authentication and password storage are separate concerns. You can change the storage without touching the flow. Real systems do exactly this: they migrate from bcrypt to argon2, or from SHA-1 to SHA-256, without changing a single route.

The lesson

A correct auth system is not a big rewrite. It's a working shape with correct storage. Get the shape right first (Stage 01). Then get the storage right (Stage 02). This ordering is the whole pedagogical point.

Hashing vs encryption — the difference that matters

One is reversible. One isn't. Passwords need the second.

The most common confusion in this space is "let's just encrypt the passwords." It sounds safer than plaintext, and it is — but it's the wrong tool. Encryption is reversible by design. Hashing is not. 

ENCRYPTION HASHING
──────────── ────────────
Two-way. One-way.
password + key -> ciphertext password -> hash
ciphertext + key -> password hash -> (impossible)

Whoever has the key can Nobody can reverse it.
read every password. Not the developer, not the
admin, not the attacker.

Correct for: Correct for:
• Messages - Passwords
• Files - Integrity checks
• PII that must be read back - Signatures
• Backups

Why hashing is the correct choice for passwords: because you should never need to read a password. The only thing you need to do with a password is check that the one the user just typed matches the one they set. And you can do that with a hash: hash the submitted password, compare to the stored hash. Same result, no reading.

Why encryption is wrong for passwords, even if it feels safer: because encryption means someone has the key. That someone can be compelled to give it up, can leak it, can be the attacker themselves. In a leaked-encrypted-passwords scenario, the passwords are effectively plaintext the moment the key is found. A leaked-hashed-passwords scenario doesn't have that failure mode — the hashes are useless without brute-force, and brute-force only works for weak passwords.

The trap: some frameworks and libraries offer password encryption and call it "secure." It's not. The pattern to remember: passwords are hashed, never encrypted. Full stop. If a vendor tells you they encrypt passwords, that's a red flag in the sales call.

Salts — why two users with the same password have different hashes

Random per user. Stored with the hash. Makes rainbow tables useless.

Without a salt, hashing "hunter2" produces the same hash for every user who uses "hunter2". That means an attacker with a leaked database can look up hashes in a precomputed table (a "rainbow table") and instantly find the password. The table is expensive to build once and then reusable against every leak.

A salt fixes this. Before hashing, add a random string unique to this user. Now "hunter2" + salt1 hashes to something different than "hunter2" + salt2. The rainbow table stops working — the attacker would need a separate table for every salt, which is the same cost as brute-forcing each password individually. 

WITHOUT SALT:
alice -> "hunter2" -> sha256 -> 5f4dcc3b...
bob -> "hunter2" -> sha256 -> 5f4dcc3b... (same hash!)

Attacker looks up "5f4dcc3b..." in a rainbow table.
Finds "hunter2". Done.

WITH SALT (werkzeug does this automatically):
alice -> "hunter2" + "x8k2" -> hash -> pbkdf2:sha256:600000$x8k2$...
bob -> "hunter2" + "m3n7" -> hash -> pbkdf2:sha256:600000$m3n7$...

Different hashes. Rainbow table useless.
Attacker must brute-force each password separately.

The good news: werkzeug.security.generate_password_hash handles salts for you automatically. You don't generate them, store them separately, or pass them around. The salt is embedded in the hash string itself.

What the hash string looks like in the database: 

pbkdf2:sha256:600000$x8k2abc$9f3e2d1c8b7a6f5e4d3c2b1a...

algorithm iterations salt hash

When check_password_hash(stored, submitted) runs, werkzeug splits the string, extracts the algorithm and salt, re-runs the same algorithm with the same salt on the submitted password, and compares the result to the stored hash. Match or no. That's the whole check.

The schema — one column renames

password becomes password_hash.

The rename isn't cosmetic. It's a statement: the column doesn't contain the password, it contains a hash of the password. That distinction matters for anyone reading the schema, for anyone writing queries against it, and for anyone thinking about what a leak would expose.

schema.sql auth-stage-02.html · lines 12–19 
CREATE TABLE users (
id INTEGER PRIMARY KEY AUTOINCREMENT,
email TEXT NOT NULL UNIQUE,
password_hash TEXT NOT NULL,
created_at TEXT NOT NULL
);
Why the column renames:

Stage 01's column was named 'password'
because it stored a password. Stage 02's
column is named 'password_hash' because
it stores a hash. The name should describe
what's actually there.

This matters for two reasons. First, a
schema is documentation - anyone reading
it should know immediately that the
column contains a hash, not a password.
Second, queries written against the column
self-document: 'SELECT password_hash FROM
users' reads as 'fetch a hash', not 'fetch
a password'.

'password_hash' is the standard name in
almost every framework: Django, Rails,
Laravel, Express examples all use it. It
signals intent.

Why TEXT and not a fixed-length type:

Hash strings vary in length depending on
the algorithm. A SHA-256 hash is 64 hex
chars plus the salt and algorithm prefix.
An argon2 hash is longer. A bcrypt hash
is 60 chars exactly.

TEXT holds all of them. If you migrated
from bcrypt to argon2 later, the column
wouldn't need to change - TEXT is big
enough for either. A VARCHAR(60) sized for
bcrypt would truncate the argon2 hash.

The rule: for hash storage, use TEXT, not
a fixed-length type. The algorithm is
variable; the column should be too.

What if the table already has data:

If Stage 01's database is live and has
plaintext passwords in a 'password' column,
a migration is needed:
1. ALTER TABLE users RENAME COLUMN
password TO password_hash
2. For each existing user, we don't know
their password, so we can't hash it.
3. Options: force a password reset,
or refuse login until reset.

The honest migration story is in the
#migrate section below. For this stage's
demo, the database is reseeded fresh, so
there's no plaintext to migrate. In a
real app, migration is a real conversation
and it's worth naming.

Register — hash before inserting

One line changes in the INSERT.

In Stage 01, the register route inserted the plaintext password. In Stage 02, it inserts the hash. That's the whole change — one line, one function call.

register.py auth-stage-02.html · lines 38–55 
from werkzeug.security import generate_password_hash

@app.route("/register", methods=["POST"])
def register():
email = request.form["email"].strip().lower()
password = request.form["password"]

with get_db() as conn:
existing = conn.execute(
"SELECT id FROM users WHERE email = ?", (email,)
).fetchone()
if existing:
return render_template("register.html", error="Email already registered."), 400

conn.execute(
"INSERT INTO users (email, password_hash, created_at) VALUES (?, ?, ?)",
(email, generate_password_hash(password), now_iso()),
)
conn.commit()

return redirect("/login")
What generate_password_hash does:

Takes a password string. Returns a hash
string. That's the whole function signature:
generate_password_hash(password) -> str

What it does internally:
1. Generate a random salt
2. Run PBKDF2-SHA256 on (password + salt)
with 600,000 iterations (default)
3. Return the result formatted as
'pbkdf2:sha256:600000`$$'

The output is a single string. It contains
everything needed to verify the password
later: the algorithm, the iteration count,
the salt, and the hash. No separate salt
column, no separate storage.

The 600,000 iterations matter: each
attempt to guess a password by brute-force
has to do 600,000 rounds of SHA-256. That's
slow on purpose. Slow means expensive to
attack. Modern GPUs can do maybe 5 billion
SHA-256 hashes per second - with PBKDF2's
600,000 iterations, that's still 8,333
attempts per second, which is much slower
than without iterations. Not unbreakable,
but 600,000x more expensive than a plain
hash.

Why the hash goes into the column, not
the password:

The column now says 'password_hash' -
storing a hash in it is consistent with
the name. Storing a password would be a
lie.

The value written is what check_password_hash
will read later. Same format, same
structure. The register route and the
login route agree on what's in the column.

Why this is the only change to register:

The route's shape is identical to Stage 01.
Parse the form, check for duplicate email,
insert the row, redirect to login. The
only line that changed is the one inside
the INSERT.

This is the payoff of Stage 01's structure.
The flow was right. Only the storage was
wrong. Fix the storage; the flow carries
forward unchanged.

Login — compare with check_password_hash

One line changes in the comparison.

The login route in Stage 01 compared plaintext with ==. Stage 02 uses check_password_hash, which splits the stored hash string, re-hashes the submitted password with the same salt, and compares. That's the whole change.

login.py auth-stage-02.html · lines 70–88 
from werkzeug.security import check_password_hash

@app.route("/login", methods=["POST"])
def login():
email = request.form["email"].strip().lower()
password = request.form["password"]

with get_db() as conn:
user = conn.execute(
"SELECT id, password_hash FROM users WHERE email = ?", (email,)
).fetchone()

if not user or not check_password_hash(user["password_hash"], password):
return render_template("login.html", error="Invalid email or password."), 401

session["user_id"] = user["id"]
return redirect("/dashboard")
What check_password_hash does:

Takes two arguments: the stored hash
string and the submitted plaintext
password. Returns True or False.

Internally:
1. Parse the stored hash string into
(algorithm, iterations, salt, hash).
2. Run the same algorithm on the
submitted password with the same
salt and iterations.
3. Compare the resulting hash to the
stored hash.
4. Return True if they match.

Everything the check needs is inside the
stored hash string. No separate salt
table. No global configuration. The hash
is self-contained.

This is why migrating from bcrypt to
argon2, or from 600,000 iterations to
1,200,000, is safe: the stored hashes
remember their own parameters. Old hashes
keep working with the old parameters;
new hashes use the new ones. You can
upgrade a user's hash on their next
successful login without knowing their
password.

The 'not user' short-circuit:

If the query returned no row (email
not found), user is None. not user
catches that. The check_password_hash
never runs on None.

Python's 'or' short-circuits: if the
left side is truthy, the right side
doesn't run. If the left is falsy
(None is falsy), the right runs.

This is why the order matters:
if not user or not check_password_hash(...)
works.
if not check_password_hash(...) or not user
crashes on None.

The pattern - check existence first,
then check credentials - is the same as
Stage 01's 'not user or user["password"]
!= password'. Only the comparison changed.

Why 'Invalid email or password' stays the
same:

Same reasoning as Stage 01: don't leak
which part failed. If the email exists
but the password is wrong, or the email
doesn't exist, the message is identical.
An attacker can't enumerate emails.

Hashing doesn't change this reasoning.
The message is a UX decision, independent
of how passwords are stored.

Why the session line doesn't change:

session["user_id"] = user["id"] works
the same in Stage 01 and Stage 02.
The session doesn't know or care how
the password was verified - by the time
we get to this line, the verification
is done. The session stores the user's
identity, not the verification method.

This is the separation of concerns that
makes the whole course work: Stage 01
built the door, Stage 02 changed the
lock. The door is the same door.

The migration — what happens to existing users

You can't hash a password you don't know. Here's the honest answer.

If you had a real Stage 01 app running with real users, and you deployed Stage 02, the column rename from password to password_hash would fail to find anything in the new column — because the old column still has plaintext. That's a real problem, and there are only two honest solutions.

Option 1 — force reset on login

The login route, on successful plaintext login, hashes the password and updates the row. The user's next login is against the hash. After the last user logs in once, the entire table is hashed.

Option 2 — delete and require reset

Delete every password (or every user). Send a reset email to all users. Every user must set a new password. Painful UX, but the table is hashed from the next login.

Option 3 — the dishonest one

Keep the plaintext column "just in case" and add a hash column beside it. This is not a migration. This is the bug persisting under a new name. Never do this.

Which to choose

Option 1 for production with existing users. Option 2 for a breach response. Option 3: never. The demo uses a fresh DB (Option 0: seed with a hashed password), so migration doesn't apply.

Why you can't hash the plaintext directly: because hashing requires knowing the password, and you shouldn't have access to plaintext passwords in the first place. Hashing isn't a reversible operation on the stored value — it's a one-time transformation of the user's input. The migration has to wait for the user to provide that input again, or force a reset.

The course demo skips this: the seed script inserts a hashed password from the start. There's no plaintext to migrate. This is the honest teaching choice — showing the migration would distract from the two-line core change. The migration pattern is described here, in the lesson text, because it's real and you'll hit it in production someday.

Next: Stage 03 — Roles

Authentication is "who are you?". Authorization is "what can you do?".

Stage 02 completed authentication. The system now knows who's logging in, safely. Stage 03 adds authorization — the layer that says "you're Alice, but Alice can't delete users."

The four big lessons in Stage 03:

  • Authentication vs authorization — one happens at login, the other on every request. Confusing them is a common security bug.
  • The role column — one column on the users table, three values: viewer, editor, admin.
  • @role_required — a second decorator, layered on top of @login_required. Same pattern, different check.
  • The "you forgot the decorator" bug — what happens when a route is protected by @login_required but not @role_required, and the viewer can delete an admin.

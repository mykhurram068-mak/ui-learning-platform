Lists & keys.
Render arrays. Get keys right.

Every app has lists. Search results, messages, notifications, cart items, comments, users. Rendering arrays of components is the most-used pattern in React — and the one with the most subtle bugs. The key prop is small, but getting it wrong causes state to attach to the wrong items, inputs to lose their values, and animations to misfire. This lesson teaches the correct pattern and every mistake that breaks lists.

🔁 .map() — the render pattern

Transform each array item into JSX. React renders the array.

The .map() method takes an array of data and returns an array of JSX. React accepts an array of elements as valid children. This is the entire pattern — you've already used it in JavaScript, and React just extends it to JSX.

    • No for loops

    You can't use a for loop to build JSX — loops don't return values from an expression. .map() does. Use .map() for rendering, for loops for side effects.

    key is special

    key is a React-internal prop. It's not passed to the child, not rendered to the DOM, and can't be read as props.key. It's used only by React's reconciliation algorithm.

    Spread for props

    passes every field of the item as props. Cleaner than name={item.name} email={item.email} when the item has many fields.

    You can't use a for loop to build a list in JSX. This is the first thing that trips up developers coming from vanilla JavaScript. JSX only accepts expressions, and a for loop is a statement. .map() is the expression version — it returns an array of JSX that JSX can render. Same for .filter(), .reduce(), and any other array method that returns a value.

    🔑 Keys — React's reconciliation primitive

    Why keys exist, what they do, and why React warns without them.

    When a list re-renders, React needs to know which items are the same as before, which are new, and which were removed. It uses the key prop to match. Without keys, React falls back to the array index — which works for static lists but breaks when items move. With stable keys, React matches each item to its previous render and preserves state, DOM nodes, and animations.

    Keys match across renders

    React compares each key to the previous render's keys. Same key = same item = preserve DOM/state. New key = new item. Missing key = removed item.

    Uniqueness among siblings

    Keys must be unique within the same array — not globally. Two different lists can use the same keys. Only siblings conflict.

    Not a prop

    You can't read props.key in the child component. React strips it. If you need the key value inside the child, pass it as a separate prop: id={item.id}.

    Required in .map()

    Every element returned from .map() needs a key. React will warn loudly if you forget. The warning is a feature — it catches silent reconciliation bugs early.

    Index-as-key bugs are silent. React doesn't error. The list renders. But state, DOM nodes, and animations attach to the wrong items when the list changes. The symptom: "my input loses focus," "my checkbox state moves to a different row," "my animation plays on the wrong item." If your list has any of these bugs, the first thing to check is whether you used index as a key.

    Safe: static lists

    Hardcoded arrays that never reorder, insert, or delete. A nav menu, a list of fixed options, a footer links list.

    Dangerous: dynamic lists

    Anything with state, reordering, filtering, or deletion. To-dos, search results, filters, sorts. These need real keys.

    Dangerous: inputs

    Any list where each item has an input (checkbox, text field). Uncontrolled inputs especially — they lose focus/value on reorder.

    The rule

    If the list can change (add, remove, reorder, filter, sort), use stable keys. If it's truly static, index is fine but unnecessary. Stable keys are always safe — index keys are only sometimes safe.

    Default to stable IDs — they're always safe. Index keys require you to reason about whether the list can ever change. That's mental overhead on every list you write. Stable IDs work unconditionally. If your data doesn't have IDs, add them at the source: { id: crypto.randomUUID(), text } when the item is created (not during render). One habit, zero bugs.

    Backend-generated id fields are the gold standard — guaranteed unique, stable, and present in the data you already have.

    Composite keys

    No single unique field? Combine fields: date + '-' + type, userId + '-' + productId. Safe if the combination is unique.

    Duplicate detection

    If you get a "duplicate key" warning, two items share a key. That's a data bug — deduplicate or use a more specific key. React renders inconsistently with duplicates.

    .filter() returns new

    Safe to chain. Doesn't mutate the original. Returns only the items where the callback returns true.

    .sort() mutates

    .sort() sorts the array in place. On state, this is a bug. Always spread first: [...items].sort(...). Or use .toSorted() (ES2023) which returns a copy.

    Always pass a comparator

    items.sort() compares as strings: [10, 9, 1] sorts to [1, 10, 9]. For numbers: (a, b) => a - b. For strings: (a, b) => a.localeCompare(b).

    Handle empty

    When the filtered array has zero items, render an empty-state message. "Nothing appears" is a bug report. "No results found" is UX.

    .sort() mutating state is one of the most common React bugs. items.sort(...) modifies the array in place — same reference — so React doesn't detect the change and doesn't re-render. The UI stays stale while the state silently changes. Worse: the mutated array now has a different order for every subsequent render, so future updates are based on wrong data. Always spread before sorting: [...items].sort(...). Or use .toSorted() which is built for this.

    ⚠️ Common mistakes

    The list and key bugs that catch every developer.

    1. Forgetting keys

    {items.map(item => )} — no key. React warns loudly. Fix: . The warning is a feature.

    2. Using index as key on dynamic lists

    Checkboxes and inputs attach to wrong items when the list changes. Silent bug. Fix: stable ID from data. Index only for static lists.

    3. Generating keys during render

    key={Math.random()} or key={crypto.randomUUID()} in the map. New key every render = React re-creates every item. Fix: generate once at data creation.

    4. Duplicate keys

    Two items share a key — React renders them inconsistently. Fix: ensure uniqueness. Combine fields if needed.

    5. Mutating array in map

    items.map(item => { item.x = 1; return item }) — mutates state items. Fix: items.map(item => ({ ...item, x: 1 })).

    6. Sorting state in place

    items.sort(...) mutates the array. Fix: [...items].sort(...) or items.toSorted(...).

    ❓ Frequently asked questions

    How do I render a list in React?

    Use .map() to transform an array of data into an array of JSX elements: {items.map(item => )}. React renders each element in order. Always include a key prop with a stable, unique value. Never use a for loop to build JSX.

    Why does React need keys?

    Keys help React identify which items have changed, been added, or been removed when the list re-renders. Without keys, React has to guess based on position, which causes bugs when items reorder or are removed.

    Should I use array index as a key?

    Almost never. Index keys cause bugs when items reorder, insert, or delete — React attaches state to the wrong item. Use a stable ID from your data instead. Index keys are safe only for static lists that never change.

    What should I use as a key?

    A stable unique identifier from your data. Usually an id field from the database (item.id). For static data without IDs, generate one with crypto.randomUUID() when the data is created — but don't generate it inside the map.

    Why does my list re-render every item on change?

    Because the key changes on every render, forcing React to treat each item as new. Common causes: generating keys inside .map(), using Math.random() as a key, or wrapping the list in an inline object that changes identity. Fix: use stable keys from your data.

    Can I use the same key twice in one list?

    No. Keys must be unique among siblings — not globally, but within the same array. Duplicate keys cause React to silently skip or overwrite items, producing wrong output.

    How do I filter or sort a list in React?

    Filter and sort before mapping: {items.filter(x => x.active).sort((a,b) => a.name.localeCompare(b.name)).map(item => )}. Both .filter() and .sort() return new arrays — never mutate the original. For sort, always pass a comparator.

    How do I render a list of fragments or multiple elements per item?

    Wrap the multiple elements in a Fragment with a key: {items.map(item =>

    {item.term}
    {item.def}
    )}. Fragments accept keys but not other props.

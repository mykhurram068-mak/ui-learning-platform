⚛️ Problem · 5 min read

"Each child should have a unique key."
The fix, and why index keys are wrong.

React renders a list with .map(), and the console warns about missing keys. Every beginner adds key={index} to silence it. Then a bug appears: deleting an item leaves the wrong state in the wrong row. This page explains why keys matter, why index keys break, and the stable-ID pattern that actually works.

Short answer: Add key={item.id} to the root element inside your .map(). Keys must be stable (same value for the same item across renders) and unique among siblings. Never use array indices if the list can reorder, insert, or delete. If your data has no ID, generate one with crypto.randomUUID() when the item is created — not during render.

✅ Solution 1 — The correct fix: stable key={item.id}

Unique ID from your data. Stable across renders. React tracks items correctly.

React uses the key prop to match elements between renders. When you add an item, React needs to know which element is new. When you delete one, React needs to know which one is gone. A stable key lets React answer those questions correctly — and only the changed element re-renders.

Key = identity

The key tells React which element is which across renders. Same key = same element = React preserves its state, DOM, focus.

Unique among siblings

Not globally unique — just within the array. Two lists can have the same keys. Only siblings compete for uniqueness.

Stable across renders

If the key changes, React treats it as a new element — remounts, loses state. Use a stable ID from your data, not Math.random().

Attach to the root

The key goes on the outermost element returned by .map(). Not on a nested child, not on a fragment wrapper.

Keys are the most misunderstood prop in React. They're not passed to the component as a prop — React intercepts them. They're not for you to use inside the component — they're for React's reconciliation algorithm. They exist for one reason: telling React "these are the same elements as last time, even if they're in a different order." Get this right and lists behave correctly forever. Get it wrong and you'll debug "why did my input lose focus" for hours.

✅ Solution 2 — Why index keys break

The bug that surfaces weeks after you ship.

Index keys seem harmless — until the list changes. When you delete an item, the item that was at index 2 becomes index 1, and React sees "the element at index 1 changed." Any state inside that element (input value, checkbox, focus, animation) stays with the index, not with the item. The result: state leaks between rows.

State leaks between rows

Delete an item, and the next row's state (input value, checkbox) moves up. Index keys make React think "same element."

Focus jumps

If an input was focused, deleting a row above it can lose focus — React didn't track that element's identity.

Animations glitch

Reordering animations with index keys play in the wrong direction because React thinks the wrong element moved.

React 18 stricter

React 18+ warns on index keys more aggressively. It's not a bug — it's React telling you the truth about a real bug.

✅ Solution 3 — Generate IDs when data has none

For local lists — form rows, optimistic UI, temp items.

Not all data has IDs. Form rows, drag-and-drop lists, optimistic UI items — these are created locally and need IDs. Generate one when the item enters the list, not on every render. crypto.randomUUID() is the modern standard — stable, unique, no dependency.

Generate when created

crypto.randomUUID() when the item enters the list. The ID then lives in state — stable across renders.

Never during render

key={crypto.randomUUID()} inside .map() produces a new key every render — full remount. Worse than the bug.

Server IDs are best

If the API returns an id, uuid, or slug, use it. It's stable, unique, and no extra work.

Fallback chain

item.id ?? item.uuid ?? item.slug for polymorphic data. All are stable. Just pick whichever the item has.

crypto.randomUUID() inside render is worse than index keys. Index keys cause state leaks on reorder; random keys force React to unmount and remount every item every render — full DOM destruction, lost focus, lost state, no animations. The fix for a missing key is a stable ID. If you can't produce a stable ID, use the index as a temporary measure — but plan to add IDs. Never use random values as keys during render.

The key mistakes that surface weeks later.

1. Using index as key

2. Using Math.random()

    5. Keys duplicated across siblings

    key={item.category} when two items share a category — duplicate key warning. Fix: unique per item.

    ... works, but <>... can't take a key. Fix: use React.Fragment key={...}.

    Doesn't help — that's for SSR mismatches. Fix: add the actual key.

    ❓ Frequently asked

    What does "Each child in a list should have a unique key" mean?

    When you render an array of elements with .map(), each returned element needs a key prop that is unique among its siblings. React uses keys to identify which items changed, were added, or were removed between renders. Without keys, React falls back to index-based reconciliation, which causes bugs when items reorder, insert, or delete.

    Why not use index as the key?

    Index keys work only if the list never reorders, inserts, or deletes. When it does, React reuses the wrong component state — inputs keep wrong values, animations jump, local state leaks between items. Use a stable ID from your data (item.id, item.uuid, item.slug).

    Do keys need to be globally unique?

    No — keys only need to be unique among siblings in the same array. Two separate .map() calls can use the same key values without conflict. The uniqueness scope is the immediate sibling set.

    What if my data has no ID?

    Generate one when the item enters the list, not on every render. If items come from an API, use whatever the server provides. If items are purely local, generate ids with crypto.randomUUID() when creating the item. Never generate a key with Math.random() inside render.

⚛️ Problem · 5 min read

"Cannot update a component while rendering."
Three fixes, one root cause.

You called setState inside render — inside the component body, not inside an event handler. React's warning is precise: renders must be pure. This page shows the three causes, the three fixes, and the underlying pattern that eliminates the bug entirely.

Short answer: Remove the setState call from render. If you're syncing state to props, don't store derived state — compute it inline or with useMemo. If you're calling setState in response to a prop change, use useEffect (still not ideal) or the key prop to remount. If you're calling setState in a child during a parent's render, move the call to an event handler or a callback. The fix always removes the setState from the render phase.

✅ Solution 1 — Don't store derived state

The most common cause. Compute, don't store.

If a value can be computed from props or other state, it doesn't belong in useState. Storing it forces you to keep it in sync — usually via useEffect or setState during render. Both are unnecessary. Compute the value directly in the render function; the compiler optimizes the rest.

derived-state.tsx 
import { useState } from 'react';

// ─── BAD: derived state in useState ──────────
function BadFullName() {
const [first, setFirst] = useState('Alice');
const [last, setLast] = useState('Smith');
const [full, setFull] = useState(first + ' ' + last); // ⚠️ derived

// ❌ Calling setState during render
setFull(first + ' ' + last);
// ⚠️ Warning: Cannot update a component while rendering

return 
{full}
;
}

const [last, setLast] = useState('Smith');

Compute during render

If a value derives from other state, compute it in the render function. No state, no sync, no warning.

useMemo for expensive

If the computation is slow, wrap in useMemo with correct dependencies. Only recomputes when deps change.

No useEffect for derivation

Even useEffect(() => setX(...), [props]) is wrong — it triggers an extra render. Compute instead.

The rule

State is for data that changes over time due to user interaction or external events. Everything else is computed.

The most common React mistake is storing too much in state. Every useState is a source of truth that can drift out of sync. If a value can be derived from other values, it should be. The bug pattern: you have props and state that disagree, and you add more state or effects to fix the disagreement. The right answer is usually to remove the derived state entirely. If you find yourself writing useEffect(() => setX(...), [something]), stop — you almost never need it. Compute the value in the render function.

✅ Solution 2 — Move setState to an event handler or effect

When the state genuinely responds to something.

Sometimes you need to update state in response to a user action or external event. That's what setState is for — but only inside event handlers, useEffect, or callbacks. Never inside render. If your code was calling setState during render to respond to a prop change, the correct fix is to move it to an event handler or use a useEffect.

Event handler

onClick, onChange, onSubmit — these call setState. That's fine. Users trigger, state updates.

useEffect for external

Fetching, subscriptions, timers. Set state inside the effect, not during render. Cleanup cancels pending updates.

key for resets

If a component should reset when props change, pass a key. React remounts with fresh state — no sync needed.

Never in render

The render function is pure. No setState, no side effects, no DOM manipulation. Just compute the JSX.

✅ Solution 3 — Move setState out of the child's render

When a child component triggers a parent update during its own render.

Another variant: a child component calls setState on the parent — or on a shared store — during its own render. React warns because the parent hasn't finished rendering yet. The fix: move the update to a callback that runs after render (event handler, effect) — or lift the state higher so the update is local.

Child → parent updates

If a child needs to inform the parent, use a callback called from an event or effect. Never call it during render.

useEffect for lifecycle

onMount runs after render via useEffect(..., []). The parent's state updates after render finishes.

Lift state up

If the parent truly owns the state, don't ask the child to set it. The parent sets it in the event that triggered the change.

Data flows down

The React mental model: props flow down, callbacks flow up. A child doesn't "set" parent state — it calls a callback the parent provided.

This warning is a real bug, not a style nit. React 18+ makes calling setState during render an error because it can produce inconsistent UI — the parent might render before the child's update lands, or the update might be discarded in concurrent mode. Fix the actual data flow. Don't wrap it in setTimeout or queueMicrotask to silence the warning — that just moves the bug to a race condition that's harder to debug.

⚠️ Common mistakes

The patterns that trigger this warning.

1. Calling setState in the component body

function Component() { setX(...); return ...; } — warning. Fix: move to event handler or useEffect.

2. Syncing props to state with setState

if (props.x !== state) setState(props.x) during render. Fix: don't store props in state. Compute or use key.

3. Using useEffect to "fix" it

useEffect(() => setX(props.x), [props.x]) — no warning, but extra render + potential stale state. Fix: derive in render.

4. Calling setState in a callback during render

{items.map(i => { if (i.bad) setX(...); return ...; })} — warning. Fix: filter in render, or dispatch in an effect.

5. Using setState in a memo selector

React 18 concurrent mode is strict about this. Fix: derive in the component, not in selectors that run during render.

6. Child triggering parent update

function Child({ onMount }) { onMount(); return ...; } — warning. Fix: useEffect(() => onMount(), []).

7. Silencing with setTimeout

setTimeout(() => setX(...), 0) inside render — moves the bug. Fix: restructure the state.

8. Not noticing this in React 17

The warning existed in React 16-17 but was easy to ignore. React 18+ is stricter. Fix: it was always a bug.

❓ Frequently asked

What does "Cannot update a component while rendering" mean in React?

It means you called setState during a component's render phase — inside the component function, not inside an event handler or effect. React renders are supposed to be pure: same props, same JSX, no side effects. Calling setState during render schedules an update to another component (or the same one), which triggers a re-render during a render.

Why did this error start appearing after I upgraded React?

React 18+ is stricter about calling setState during render. The warning existed in React 16-17 but was easier to ignore. React 18 added concurrency features that make the warning a hard error in some cases. The fix is the same: don't call setState during render.

How do I fix it if I need to derive state from props?

Don't store derived state in useState. Compute it inline: instead of const [full, setFull] = useState(first + ' ' + last), write const full = first + ' ' + last. If computation is expensive, wrap in useMemo. If you must sync, use the key prop to remount the component when the input changes.

What is the difference between calling setState during render vs inside useEffect?

setState during render happens synchronously as React renders — it interrupts the render with a new render, which is what causes the warning. setState inside useEffect runs after the render completes, so React schedules another render normally. Effect-based setState is also not ideal but it's not a warning.

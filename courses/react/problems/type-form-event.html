"Parameter 'e' implicitly has an 'any' type."
Three causes, three fixes.

The form handler every TypeScript + React project hits. You wrote onChange={'{e => setEmail(e.target.value)}'} and the compiler either complains about any, or about target not existing on Event. Both are the same bug: the event parameter isn't typed, so React's specific event type is lost. This page covers the three causes, the three fixes, and the correct event types for onChange, onSubmit, and onClick.

Short answer: Type the event, not any. Use React.ChangeEvent for inputs, React.FormEvent for forms, React.MouseEvent for buttons. Import the types from 'react' — not the DOM. The three causes: (1) no annotation on an inline handler, (2) the handler was extracted to a function, (3) the wrong event type (Event instead of ChangeEvent). Fix each at the parameter — never cast to any.

✅ Solution 1 — No annotation on an inline handler

The most common cause: onChange={'{e => ...}'} with no type.

When the handler is inline and the parameter isn't annotated, TypeScript can't infer it in some configs — especially with noImplicitAny on. The compiler falls back to any and you lose e.target.value. Fix: annotate the parameter explicitly.

The React event for onChange on inputs, textareas, selects. T is the element type.

HTMLInputElement

For . Has value, checked, files. Not the generic Event.

✅ Solution 2 — Handler extracted to a function

The type is lost the moment the handler leaves the JSX.

Inline handlers get inferred from the JSX attribute. Named handlers don't — they're standalone functions. The compiler can't see which element calls them, so it defaults to any under noImplicitAny. Fix: type the entire function signature.

Annotate named handlers

Moving a handler out of JSX loses inference. Type the parameter: (e: ChangeEvent).

ChangeEventHandler

The function type for onChange. Use it when typing the whole handler: const h: ChangeEventHandler = ...

FormEvent vs ChangeEvent

onSubmit uses FormEvent. onChange uses ChangeEvent. They are not interchangeable.

One handler, many fields

Use e.target.name to route. Type the parameter once. The dynamic key needs a cast to the field union.

✅ Solution 3 — Wrong event type

Event, any, or FormEvent on an input — all fail.

Two related mistakes. (1) You typed the parameter as the DOM base Event — it has no target.value, so .value fails. (2) You typed it as FormEvent on an input's onChange — wrong event family. React's synthetic events are specific: ChangeEvent for inputs, FormEvent for forms, MouseEvent for clicks. Fix: use the event that matches the attribute.

Never use DOM Event

The DOM base type has no .value. React's ChangeEvent narrows the target to the element type.

Match event to attribute

onChange → ChangeEvent. onSubmit → FormEvent. onClick → MouseEvent. Never mix.

Import from 'react'

ChangeEvent, FormEvent, MouseEvent are React types. Importing from the DOM gives you the wrong (native) event.

Element matters

HTMLInputElement for inputs, HTMLTextAreaElement for textareas, HTMLSelectElement for selects.

Don't cast e to any to silence the error. (e as any).target.value compiles, but you lose autocomplete, you lose null-safety on target, and you reintroduce the bug on the next refactor. The right fix is the correct event type — ChangeEvent. It's one annotation, and it unlocks every property on the target for free.

⚠️ Common mistakes

The type errors that cost real time.

1. Unannotated inline handler

onChange={'{e => ...}'} with no type under noImplicitAny. Fix: annotate or let React infer on a known element.

2. Unannotated named handler

Moving the handler out of JSX drops inference. Fix: (e: ChangeEvent).

3. Typing as DOM Event

(e: Event) has no .value. Fix: use React's ChangeEvent, not the DOM Event.

4. FormEvent on an input

onChange={'{(e: FormEvent) => ...}'} — wrong family. Fix: ChangeEvent.

5. e.target.value on a select

Selects use ChangeEvent. Same .value, different element type.

6. Casting e as any

Silences the error, loses all safety. Fix: the correct event type.

7. Forgetting e.preventDefault()

The form reloads the page on submit. Fix: call it first thing in handleSubmit.

8. Importing events from the DOM

import { Event } from 'react' — wrong. React has its own synthetic event types. Import from 'react'.

❓ Frequently asked

How do I fix "Parameter 'e' implicitly has an 'any' type" in React?

Three causes, three fixes. (1) Inline handler with no type — annotate the parameter: (e: React.ChangeEvent). (2) Handler extracted to a function — type the whole function signature. (3) Generic event passed in — use the specific event type (ChangeEvent, FormEvent, MouseEvent) from React, never the DOM Event type.

What is the difference between ChangeEvent, FormEvent, and MouseEvent in React?

ChangeEvent fires when an input's value changes — use it for onChange on inputs, textareas, and selects. Its target is typed to the specific element, so e.target.value works. FormEvent fires when a form is submitted — use it for onSubmit on form. It does not have a value; call e.preventDefault() to stop the page reload. MouseEvent fires on click handlers — use it for onClick on buttons and links. Each is a React synthetic event, not the native DOM Event. Import them from 'react', not from the DOM.

Why does e.target.value fail on type 'Event'?

The DOM base type Event has no value property — only specific targets do. React's synthetic events narrow the target based on the element type. If you type the parameter as Event (or let it default to any), TypeScript can't see the value. Fix: type the parameter as React.ChangeEvent. The target is then HTMLInputElement, which has value, checked, files, etc. Use HTMLTextAreaElement for textareas and HTMLSelectElement for selects.

Should I use React.FormEvent or just FormEvent?

Use React.FormEvent when you access form-specific properties like e.currentTarget.elements. The generic parameter narrows currentTarget. For the common case — e.preventDefault() only — React.FormEvent is enough and simpler. Both work on onSubmit. The generic is only needed when you reach into the form's elements, which most handlers don't.

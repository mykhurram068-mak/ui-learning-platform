"Objects are not valid as a React child."
Three causes, three fixes.

Two versions of the same bug. At runtime, React throws Objects are not valid as a React child. At compile time, TypeScript throws Type 'X' is not assignable to type 'ReactNode'. Both mean the same thing: you're trying to render something React can't display — an object, a Date, a Map, or a function. This page covers the three causes, the three fixes, and the correct way to type children.

Short answer: Render primitives, elements, or nothing. Type children as ReactNode, not ReactElement or JSX.Element. The three causes: (1) you rendered an object ({'{user}'} instead of {'{user.name}'}), (2) you rendered a non-primitive like Date, Map, or Set, (3) you put a function in JSX instead of calling it, or forgot that children can be a render prop. Fix each at the source — don't String() everything.

✅ Solution 1 — Rendering an object

The most common cause: {'{user}'} when you meant {'{user.name}'}.

React renders strings, numbers, and elements. A plain object is none of these. If you put {'{user}'} in JSX, React throws at render time. TypeScript catches this earlier — User is not assignable to ReactNode. Fix: render a specific field, or stringify for debugging.

ReactNode = primitives + elements

string | number | boolean | null | undefined | ReactElement | Iterable. Objects are not included.

{'{user}'} is the bug

You meant a field. {'{user.name}'}, {'{user.email}'}. Never the whole object.

JSON.stringify for debug

Returns a string — valid child. Use 

 to preserve formatting. Never ship this to users.

Object.entries for generic render

Turns an object into an array of [key, value] pairs. Values must be primitives to render.

✅ Solution 2 — Rendering a non-primitive

Date, Map, Set, class instance — all objects, all crash.

Date, Map, Set, and class instances are objects. React can't render them — it renders the object, and throws. Fix: convert to a primitive or an array before rendering. Date → .toLocaleDateString(). Map → Array.from(map). Set → [...set].

Date → format

date.toLocaleDateString(), date.toISOString(), or a formatter. Never render the raw Date.

Map → Array.from

Array.from(map) gives [key, value][]. [map.keys()] and [map.values()] also work.

Set → spread

[...set] gives an array. Array.from(set) does the same. Both are valid children after .map.

Class → method call

If the class has a toString() or format(), call it. React won't call it for you.

✅ Solution 3 — Functions and children typing

onClick={'{handleClick()}'} and the ReactNode vs ReactElement trap.

Two related mistakes. (1) You called a function in JSX instead of passing it: onClick={'{handleClick()}'} runs on render, and if it returns an object, React crashes. (2) You typed children as ReactElement or JSX.Element — too narrow. children can be a string, number, array, null, or element. Type it as ReactNode.

functions-and-children.tsx 
import { ReactNode, ReactElement, useState } from 'react';

// ─── BAD: calling a function in JSX ──────────
function BadButton() {
const handleClick = () => ({ message: 'clicked' });

// ❌ onClick runs immediately, returns an object,
// and that object is passed as the onClick prop.
// React warns: "Expected onClick to be a function, got [object Object]"
// Worse: if you render the return value, it crashes.
return ;
}

// ─── GOOD 1: pass the function reference ────
function GoodButton() {
const handleClick = () => ({ message: 'clicked' });

// ✅ Function reference — React calls it on click
return ;
}

// ─── GOOD 2: inline arrow when you need args ──
function ButtonWithArg() {
const log = (msg: string) => console.log(msg);

// ✅ Arrow wrapper — calls log on click, not on render
return ;
}

// ─── BAD: children typed as ReactElement ─────
interface BadCardProps {
// ❌ Too narrow. hello is a string, not an element.
// ❌ {null} is null, not an element.
children: ReactElement;
}

function BadCard({ children }: BadCardProps) {
return 
{children}
;
}

// ─── GOOD 3: children typed as ReactNode ─────
interface CardProps {
// ✅ Accepts strings, numbers, elements, arrays, null
children: ReactNode;
}

function Card({ children }: CardProps) {
return 
{children}
;
}

// ─── GOOD 4: render prop (function children) ──
interface DataLoaderProps {
// ✅ Explicitly a function — must be declared, not default
children: (data: string) => ReactNode;
}

function DataLoader({ children }: DataLoaderProps) {
const [data] = useState('loaded data');
// ✅ Call the function with the data — not {children}
return 
{children(data)}
;
}

// ─── Usage ───────────────────────────────────
function App() {
return (


{/* ✅ children as string — works with ReactNode */}
hello

{/* ✅ children as element */}

hello


{/* ✅ children as null — works with ReactNode */}
{null}

{/* ✅ render prop — function children */}

{(data) => 
{data}
}



);
}

children: ReactNode

Widest type. Accepts strings, numbers, elements, arrays, null, undefined. Use this for children always.

ReactElement is narrow

Only a single JSX element. Fails on hello (string) and {'{null}'} (null).

Pass the function, don't call it

onClick={'{handleClick}'} — not onClick={'{handleClick()}'}. Wrap in an arrow if you need args.

Render props need explicit typing

children: (data: T) => ReactNode. The default ReactNode excludes functions — you opt in.

Don't reach for String(x) to silence the error. Wrapping everything in String(user) gives you "[object Object]" — a string, so React stops complaining, but the output is garbage. The right fix is to render the specific fields you want, format non-primitives (Date, Map, Set) explicitly, and type children as ReactNode. String() is a symptom patch, not a fix.

⚠️ Common mistakes

The crash patterns that cost real time.

1. Rendering a whole object

{'{user}'} instead of {'{user.name}'}. Fix: render the field, not the object.

2. Rendering a Date

{'{createdAt}'} where createdAt is a Date. Fix: {'{createdAt.toLocaleDateString()}'}.

3. Rendering a Map or Set

{'{scores}'} when scores is a Map. Fix: {'Array.from(scores).map(...)'}.

4. Typing children as ReactElement

Fails on strings and null. Fix: children: ReactNode.

5. Calling a function in JSX

onClick={'{handleClick()}'} runs on render. Fix: onClick={'{handleClick}'} or onClick={'{() => handleClick(arg)}'}.

6. String() as a workaround

{'String(user)'} gives "[object Object]". Fix: render the fields you need.

7. Returning an object from .map()

{'items.map(i => ({ name: i.name }))'} returns objects. Fix: return an element: {'items.map(i =>

  • {i.name}
    • )'}.

    8. Forgetting that children can be a function

    Render-prop children need (data: T) => ReactNode typing, not ReactNode. Fix: declare the function signature.

    ❓ Frequently asked

    How do I fix "Objects are not valid as a React child" in React?

    Three causes, three fixes. (1) Rendering an object directly — render a specific field (user.name) or JSON.stringify(obj) for debug. (2) Rendering a Date or Map/Set — call .toISOString(), Array.from(map), or format explicitly. (3) Forgetting to call a function, or passing a function where a node is expected. Never put {someObject} inside JSX — always extract a primitive or wrap in a component.

    What is the difference between ReactNode, ReactElement, and JSX.Element?;

    ReactNode is the widest type — it includes string, number, boolean, null, undefined, ReactElement, and iterables of ReactNode. ReactElement is the object that createElement returns (a single JSX element). JSX.Element is ReactElement with a specific props type. For children props, always use ReactNode — it accepts everything React can render. Use ReactElement only when you need to access element internals (type, props).

    Why does React complain about a Date object as a child?

    React only renders strings, numbers, and elements. A Date is an object — React doesn't know how to display it. Fix: convert it first. Use date.toLocaleDateString(), date.toISOString(), or a formatting library. Same applies to Map, Set, and any class instance. If it's not a primitive or a ReactElement, React throws.

    Can children be a function in React?

    Yes — this is the "function as children" / render prop pattern. The child prop is typed as (data: T) => ReactNode, not ReactNode. You opt into it explicitly: interface Props { children: (user: User) => ReactNode }. Then the component calls children(user) instead of rendering {children}. This is not the default children type — it must be declared. React's built-in children type is ReactNode, which excludes functions.

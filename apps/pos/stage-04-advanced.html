Stage 03 gave the POS a real transaction. Stage 04 gives it the rest of what a working register needs: refunds as reversal sales (never deletes — accounting), a Z-report that reconciles the till (sales total must equal payments total, or something is wrong), hold/resume so a cashier can park a cart, printable 80mm receipts via @media print, and product archiving — because the RESTRICT constraint from Stage 03 means you can't delete a sold product, so you hide it instead.

This is the final stage. After it, the POS & Billing build is complete: four stages, three tables, an atomic checkout, reversal-based refunds, and a till that balances. No Stage 05.

✅ Refunds — reversal, not deletion

You don't un-happen a transaction. You record its reversal.

What a refund is

A new sale with negative quantities, negative totals, and a negative payment. It points at the original via refund_of_sale_id.

What a refund is not

A DELETE on the original. The customer really did buy the item yesterday. That fact is still true. Today it was returned.

The stock flow

A stock_movements row with reason='refunded' and a positive delta. Stock goes back up. Inventory's audit log shows the return.

The safeguards

Refund refuses if: the sale isn't paid, it's itself a refund, or it's already been refunded. Double-refunds are impossible.

refund.py 
@app.route("/api/sales/<int:sid>/refund", methods=["POST"])
def refund_sale(sid):
    data = request.get_json(silent=True) or {}
    note = (data.get("note") or "").strip() or f"Refund of sale #{sid}"

    with get_db() as conn:
        original = conn.execute(
            "SELECT * FROM sales WHERE id = ?", (sid,)
        ).fetchone()
        if not original:
            return jsonify({"error": "Sale not found."}), 404
        if original["status"] != "paid":
            return jsonify({
                "error": f"Only paid sales can be refunded "
                         f"(status is '{original['status']}')."
            }), 400
        if original["refund_of_sale_id"] is not None:
            return jsonify({
                "error": "This sale is itself a refund and cannot be refunded."
            }), 400

        # Guard: already refunded?
        existing = conn.execute(
            "SELECT id FROM sales WHERE refund_of_sale_id = ?", (sid,)
        ).fetchone()
        if existing:
            return jsonify({
                "error": f"Sale #{sid} already refunded "
                         f"(refund #{existing['id']})."
            }), 409

        original_lines = conn.execute(
            "SELECT * FROM sale_lines WHERE sale_id = ?", (sid,)
        ).fetchall()
        original_payment = conn.execute(
            "SELECT * FROM payments WHERE sale_id = ?", (sid,)
        ).fetchone()

        timestamp = now_iso()

        # Insert reversal sale — negative totals, points at the parent
        cur = conn.execute(
            """INSERT INTO sales
               (cashier, subtotal, tax_rate, tax_total, grand_total,
                status, refund_of_sale_id, created_at, paid_at)
               VALUES (?, ?, ?, ?, ?, 'paid', ?, ?, ?)""",
            (
                original["cashier"],
                -original["subtotal"],
                original["tax_rate"],
                -original["tax_total"],
                -original["grand_total"],
                sid, timestamp, timestamp,
            ),
        )
        refund_id = cur.lastrowid

        # Reverse every line
        for line in original_lines:
            conn.execute(
                """INSERT INTO sale_lines
                   (sale_id, product_id, product_name, qty,
                    unit_price, line_total, created_at)
                   VALUES (?, ?, ?, ?, ?, ?, ?)""",
                (refund_id, line["product_id"], line["product_name"],
                 -line["qty"], line["unit_price"], -line["line_total"], timestamp),
            )
            # Stock goes back up
            conn.execute(
                """INSERT INTO stock_movements
                   (product_id, delta, reason, note, created_at)
                   VALUES (?, ?, 'refunded', ?, ?)""",
                (line["product_id"], line["qty"],
                 f"Refund of sale #{sid}", timestamp),
            )
            conn.execute(
                """UPDATE products
                   SET quantity = quantity + ?, updated_at = ?
                   WHERE id = ?""",
                (line["qty"], timestamp, line["product_id"]),
            )

        # Reversal payment — negative amount
        conn.execute(
            """INSERT INTO payments
               (sale_id, method, amount, tendered, change, created_at)
               VALUES (?, ?, ?, ?, 0, ?)""",
            (refund_id, original_payment["method"],
             -original_payment["amount"], -original_payment["amount"], timestamp),
        )

        refund = _fetch_sale(conn, refund_id)

    refund["refund_note"] = note
    return jsonify(refund), 201

Why a refund is a NEW sale, not a modification:

  Imagine you delete sale #42 because the
  customer returned everything.

    sale #42: GONE
    lines: GONE
    payment: GONE

  Every report that ever included #42 is now
  wrong. Yesterday's revenue was $500 — today
  it's $410 because a sale vanished from the
  books. The audit trail has a hole.

  If a manager asks "who processed sale #42?"
  the answer is "no one — it doesn't exist."
  That's a compliance failure in any real
  business.

  Now imagine you create refund sale #88
  pointing at #42:

    sale #42: paid, $89.00, still there
    sale #88: refund, -$89.00, refund_of_sale_id = 42
    Net for the day: $0.00 (89 - 89)
    Audit log: "Refund #88 reverses sale #42
                on Nov 14, reason: damaged item."

  Every report is correct. Every audit trail
  is complete. Every query that sums
  `sales.grand_total` for the day gets $0,
  which is the truth.

  This is the foundational rule of accounting:
  records are immutable. You don't edit the
  past. You record corrections as new
  entries that reference the past.

Why the three guards:

  1. status != 'paid'
     Can't refund a held sale (never paid)
     Can't refund a voided sale (already gone)
     Can't refund an already-refunded sale
     (it's a refund, see guard 2)

  2. refund_of_sale_id IS NOT NULL
     This is a refund. Refunding a refund
     would be refunding money the customer
     never paid. Nonsense. 400.

  3. existing refund with refund_of_sale_id = sid
     Sale #42 has already been refunded by #88.
     Trying to refund it again would create
     #99 that also reverses #42 — the customer
     would get double their money back.
     409 conflict, include the refund #ID
     so the cashier can look it up.

Why the stock movement delta is positive:

  A 'sold' movement has delta = -qty
  (stock went down).

  A 'refunded' movement has delta = +qty
  (stock went back up).

  Both are movements. Both are logged.
  The sum of all movements for a product
  equals its current quantity (the invariant
  from Inventory Stage 04).

  If you deleted the 'sold' movement instead
  of adding a 'refunded' one, the audit log
  would show the item was never sold. Wrong —
  it WAS sold, then returned. Two events,
  two log rows.

Why the negative payment amount:

  Same reason. The books need to net to zero.
  Sale #42: +$89.00 payment.
  Refund #88: -$89.00 payment.
  Sum for the day: $0.

  If you deleted the payment instead, the
  sum would be $0 too — but the books would
  show one payment instead of two opposite
  ones. The audit trail loses the reversal.

  Storing both is the correct approach for
  reconciliation. The Z-report proves it.

✅ Z-report — reconcile the till

Two independent sums must match. If they don't, investigate.

A Z-report answers one question: does the money in the till match the money the books say should be there? It computes two numbers independently and compares them:

Net sales (books)

SUM(grand_total) for all paid sales on the day. Includes refunds — refund sales have negative grand_total, so they subtract.

Payments total (money)

SUM(amount) for all payment rows on the day. Refund payments have negative amount — they subtract too.

The check

payments_total == net_sales → reconciles: true. If false, a sale or payment was written outside the checkout, or one was tampered with.

zreport.py 
@app.route("/api/reports/z", methods=["GET"])
def z_report():
    d = request.args.get("date") or date.today().isoformat()
    day_start = d + "T00:00:00"
    day_end   = d + "T23:59:59"

    with get_db() as conn:
        # Books side: sales totals, split by refund vs original
        row = conn.execute(
            """SELECT
                 COALESCE(SUM(CASE WHEN refund_of_sale_id IS NULL
                                   THEN grand_total ELSE 0 END), 0) AS gross_sales,
                 COALESCE(SUM(CASE WHEN refund_of_sale_id IS NOT NULL
                                   THEN grand_total ELSE 0 END), 0) AS refunds,
                 COALESCE(SUM(CASE WHEN refund_of_sale_id IS NULL
                                   THEN tax_total ELSE 0 END), 0) AS tax_collected,
                 COUNT(CASE WHEN refund_of_sale_id IS NULL
                            AND status='paid' THEN 1 END) AS sale_count,
                 COUNT(CASE WHEN refund_of_sale_id IS NOT NULL
                            THEN 1 END) AS refund_count
               FROM sales
               WHERE status = 'paid'
                 AND created_at BETWEEN ? AND ?""",
            (day_start, day_end),
        ).fetchone()

        gross   = round_money(row["gross_sales"])
        refunds = round_money(row["refunds"])
        net     = round_money(gross + refunds)
        tax     = round_money(row["tax_collected"])

        # Money side: payments by method (gross only, no refunds)
        method_rows = conn.execute(
            """SELECT p.method, COALESCE(SUM(p.amount), 0) AS total
               FROM payments p
               JOIN sales s ON s.id = p.sale_id
               WHERE s.status = 'paid'
                 AND s.created_at BETWEEN ? AND ?
                 AND s.refund_of_sale_id IS NULL
               GROUP BY p.method""",
            (day_start, day_end),
        ).fetchall()
        by_method = {r["method"]: round_money(r["total"]) for r in method_rows}

        # Money side: ALL payments (gross + refund payments, netted)
        payments_total_row = conn.execute(
            """SELECT COALESCE(SUM(p.amount), 0) AS total
               FROM payments p
               JOIN sales s ON s.id = p.sale_id
               WHERE s.status = 'paid'
                 AND s.created_at BETWEEN ? AND ?""",
            (day_start, day_end),
        ).fetchone()
        payments_total = round_money(payments_total_row["total"])

    reconciles = abs(payments_total - net) < 0.01

    return jsonify({
        "date": d,
        "gross_sales": gross,
        "refunds": refunds,
        "net_sales": net,
        "tax_collected": tax,
        "sale_count": row["sale_count"],
        "refund_count": row["refund_count"],
        "by_method": by_method,
        "payments_total": payments_total,
        "reconciles": reconciles,
    })

Why "net sales" and "payments total" must match:

  Every sale that is paid MUST have a payment
  row. Every payment row MUST belong to a sale.
  This is enforced by the atomic checkout — both
  INSERTs happen in one transaction, or neither
  does.

  So the sum of grand_total on paid sales should
  always equal the sum of amount on payments for
  those same sales. Same set of rows, same total.

  When it doesn't, one of these happened:

    → A sale was INSERTed without a payment
      (manual SQL, bug in the checkout)
    → A payment was INSERTed without a sale
      (FK should prevent this, but check)
    → Someone UPDATE'd a payment amount
      (tampering, or a refund done wrong)
    → Someone DELETE'd a payment
      (should CASCADE with the sale, but check)
    → A rounding bug in one of the two sums
      (unlikely with round_money, but possible)

  The Z-report can't tell you WHICH happened.
  It just says "the books don't match the money."
  The next step is a manual diff — find the
  sale/payment pair that disagrees. The report
  is the alarm; the investigation is the fire
  drill.

Why the tolerance is 0.01:

  Floating-point money math isn't exact.
  $89.00 stored as a float might be
  88.99999999 or 89.00000001. The sums
  across hundreds of rows can drift by a
  fraction of a cent.

  So "equal" means abs(diff) < 0.01. One
  cent of tolerance. Anything within a penny
  is rounding noise; anything beyond is a
  real discrepancy.

  In a strict system you'd store money as
  INTEGER cents, not REAL dollars. That
  eliminates float drift entirely. We used
  REAL for simplicity — a real POS would
  use integers. The lesson: know what you
  chose and why.

Why by_method excludes refunds:

  The Z-report has two jobs:
    1. Reconcile: does payments match sales?
       (all payments, including refunds)
    2. Cash handling: how much cash, how much
       card? (gross only, before refunds)

  Mixing them would be confusing. "Cash: $450
  (net of $50 in refunds)" is harder to
  reconcile against a physical till than
  "Cash in: $500. Cash out (refunds): $50."

  So by_method is gross-only, and refunds are
  reported separately. The reconciliation uses
  net (gross + refunds). Two views of the same
  money, for two different purposes.

  This is why Z-reports in real POS systems
  have many columns. Each one answers a
  specific cash-handling question.

✅ Hold/resume — park a cart

A held sale is a saved cart. It does not reserve stock.

The scenario

A cashier is building a cart. The customer realizes they forgot something and goes back. The cashier needs to serve the next person.

The hold

POST the cart to /api/sales/hold. Saved with status='held'. Stock untouched. The cashier's screen is now free.

The resume

Click Held → the list shows parked carts → Resume loads the lines into the current cart. The held sale is voided (it was never paid).

Why no stock reservation

Because a held sale is not a completed transaction. If holding reserved stock, an abandoned cart would lock inventory forever. Stock is checked at checkout time, not hold time.

hold.py 
@app.route("/api/sales/hold", methods=["POST"])
def hold_sale():
    """
    Park a cart. Unlike create_sale, this does NOT
    touch stock — a held sale is not a completed
    transaction.
    """
    data = request.get_json(silent=True) or {}
    lines = data.get("lines") or []
    tax_rate = float(data.get("taxRate", 8.5))
    cashier = (data.get("cashier") or "Alex Rivera").strip()

    if not lines:
        return jsonify({"error": "Cannot hold an empty cart."}), 400

    with get_db() as conn:
        # Validate products exist; no stock check
        resolved = []
        subtotal = 0.0
        for raw in lines:
            pid = int(raw["productId"])
            qty = int(raw["qty"])
            if qty <= 0:
                return jsonify({"error": "Quantity must be positive."}), 400

            p = conn.execute(
                """SELECT id, name, price FROM products
                   WHERE id = ? AND archived_at IS NULL""",
                (pid,),
            ).fetchone()
            if not p:
                return jsonify({
                    "error": f"Product {pid} not found or archived."
                }), 404

            lt = round_money(p["price"] * qty)
            subtotal += lt
            resolved.append({
                "product_id": p["id"], "name": p["name"],
                "qty": qty, "unit_price": p["price"], "line_total": lt,
            })

        subtotal = round_money(subtotal)
        tax_total = round_money(subtotal * tax_rate / 100)
        grand_total = round_money(subtotal + tax_total)
        timestamp = now_iso()

        cur = conn.execute(
            """INSERT INTO sales
               (cashier, subtotal, tax_rate, tax_total, grand_total,
                status, refund_of_sale_id, created_at, paid_at)
               VALUES (?, ?, ?, ?, ?, 'held', NULL, ?, NULL)""",
            (cashier, subtotal, tax_rate, tax_total, grand_total, timestamp),
        )
        sale_id = cur.lastrowid

        for r in resolved:
            conn.execute(
                """INSERT INTO sale_lines
                   (sale_id, product_id, product_name, qty,
                    unit_price, line_total, created_at)
                   VALUES (?, ?, ?, ?, ?, ?, ?)""",
                (sale_id, r["product_id"], r["name"], r["qty"],
                 r["unit_price"], r["line_total"], timestamp),
            )

        sale = _fetch_sale(conn, sale_id)

    return jsonify(sale), 201


@app.route("/api/sales/<int:sid>/resume", methods=["POST"])
def resume_sale(sid):
    """Return a held sale's lines so the frontend can load them."""
    with get_db() as conn:
        sale = conn.execute(
            "SELECT * FROM sales WHERE id = ?", (sid,)
        ).fetchone()
        if not sale:
            return jsonify({"error": "Sale not found."}), 404
        if sale["status"] != "held":
            return jsonify({
                "error": f"Sale #{sid} is not held "
                         f"(status '{sale['status']}')."
            }), 400

        sale = _fetch_sale(conn, sid)

    return jsonify(sale)


@app.route("/api/sales/<int:sid>/void", methods=["POST"])
def void_held_sale(sid):
    """Delete a held sale. Safe: held sales never touched stock."""
    with get_db() as conn:
        sale = conn.execute(
            "SELECT * FROM sales WHERE id = ?", (sid,)
        ).fetchone()
        if not sale:
            return jsonify({"error": "Sale not found."}), 404
        if sale["status"] != "held":
            return jsonify({
                "error": "Only held sales can be voided."
            }), 400
        conn.execute("DELETE FROM sales WHERE id = ?", (sid,))
        conn.commit()

    return jsonify({"ok": True})

            (cashier, subtotal, tax_rate, tax_total, grand_total, timestamp),
        )
        sale_id = cur.lastrowid

        for r in resolved:
            conn.execute(
                """INSERT INTO sale_lines
                   (sale_id, product_id, product_name, qty,
                    unit_price, line_total, created_at)
                   VALUES (?, ?, ?, ?, ?, ?, ?)""",
                (sale_id, r["product_id"], r["name"], r["qty"],
                 r["unit_price"], r["line_total"], timestamp),
            )

        sale = _fetch_sale(conn, sale_id)

    return jsonify(sale), 201


@app.route("/api/sales//resume", methods=["POST"])
def resume_sale(sid):
    """Return a held sale's lines so the frontend can load them."""
    with get_db() as conn:
        sale = conn.execute(
            "SELECT * FROM sales WHERE id = ?", (sid,)
        ).fetchone()
        if not sale:
            return jsonify({"error": "Sale not found."}), 404
        if sale["status"] != "held":
            return jsonify({
                "error": f"Sale #{sid} is not held "
                         f"(status '{sale['status']}')."
            }), 400

        sale = _fetch_sale(conn, sid)

    return jsonify(sale)


@app.route("/api/sales//void", methods=["POST"])
def void_held_sale(sid):
    """Delete a held sale. Safe: held sales never touched stock."""
    with get_db() as conn:
        sale = conn.execute(
            "SELECT * FROM sales WHERE id = ?", (sid,)
        ).fetchone()
        if not sale:
            return jsonify({"error": "Sale not found."}), 404
        if sale["status"] != "held":
            return jsonify({
                "error": "Only held sales can be voided."
            }), 400
        conn.execute("DELETE FROM sales WHERE id = ?", (sid,))
        conn.commit()

    return jsonify({"ok": True})
Why hold doesn't touch stock:

  Scenario A — hold reserves stock:
    Cashier holds a cart with 2 keyboards.
    Cashier forgets about it.
    Customer walks away.
    → 2 keyboards are "reserved" forever.
    → Stock says 0 but the physical shelf
       has 2 units. Inventory drifts.

  Scenario B — hold does NOT reserve stock:
    Cashier holds a cart with 2 keyboards.
    Another cashier sells all 8 keyboards.
    Cashier 1 resumes the held cart.
    Checkout fails: "only 0 in stock."
    Cashier 1 apologizes, cashier 2 already
    sold the units. Correct behavior.

  B is correct. A held cart is a bookmarked
  shopping list. It has no reserved allocation.
  Stock is checked at the moment of sale —
  the atomic checkout — because that's when
  the transaction becomes real.

Why the resume flow voids the held sale:

  The frontend does this sequence:
    1. POST /api/sales/42/resume → get lines
    2. Load lines into current cart
    3. POST /api/sales/42/void → delete held sale

  The held sale existed to hold the lines.
  Once the lines are in the cashier's cart,
  the held sale has done its job. Keeping it
  would leave a stale "held" record that
  looks like a parked cart nobody's working on.

  Voiding it is idempotent — if it fails (race,
  double-click), the held sale is still there
  and the cashier can void it manually from
  the Held panel. The cart doesn't lose state.

Why only held sales can be voided:

  A paid sale can't be voided — it needs a
  refund instead (reversal). A void on a paid
  sale would delete the record and break every
  report.

  A held sale has no payment and no stock
  movements. Deleting it is safe — there's
  nothing to reverse. The status check
  enforces this: only status='held' allows DELETE.

  This is the same "financial records are
  immutable" principle, applied differently.
  A held sale is a draft; drafts can be deleted.
  A paid sale is a record; records can only
  be reversed.

Why visibility:hidden, not display:none:

  display:none would remove the receipt
  from layout too, since it's inside
  body. You'd have to be very careful
  about which selectors re-show it.

  visibility:hidden keeps everything in
  layout but invisible. The receipt modal
  gets visibility:visible, so it appears
  exactly where it was — no layout shift,
  no fighting with positioning.

  This is the standard pattern for print-only
  sections that need to isolate one element:
  hide the root, show the target.

Why @page { size: 80mm auto }:

  Thermal receipt printers use 80mm paper
  (sometimes 58mm). Without @page size,
  the browser prints to the default paper
  size — usually A4 or Letter — with the
  80mm receipt content crammed into the
  top-left corner.

  With size:80mm auto, the browser asks
  the printer "give me a 80mm-wide page,
  however tall." Thermal printers accept
  this and print a receipt exactly as wide
  as the paper roll. Auto height means the
  page ends where the content ends, not at
  a fixed A4 height with wasted blank space.

Why margin:0 on @page:

  Thermal paper has no printable margin —
  the printer head runs edge to edge. If
  you leave margin:0.5in from a default
  @page, the receipt is indented and might
  clip on the right. Set it to 0 and let
  the receipt's own padding (4mm) provide
  the visual breathing room.

Why 10pt font size:

  Screen size (0.75rem ≈ 12px) is fine for
  a monitor at arm's length. On paper, 12px
  is too small for a cashier to read at a
  glance. 10pt on paper ≈ 13.3px, which
  reads comfortably at typical receipt
  reading distance.

  Real thermal receipts use 9–11pt. 10pt
  is the standard middle. If you need
  different sizes for "store name" vs
  "line items," use relative sizes within
  the 10pt base.

Why we hide .pos-modal-header:

  The "Receipt" title and the × close
  button belong on the screen UI, not on
  the printed receipt. A real receipt
  doesn't say "Receipt" at the top of a
  modal — it starts with the store name.

  Same for .pos-receipt-actions (Close
  and Print buttons). Those are chrome.

The trigger:

  document.getElementById('print-btn')
    .addEventListener('click', () =>
      window.print());

  window.print() opens the OS print dialog.
  The @media print rules apply only for the
  duration of that dialog. When it closes,
  the page returns to its normal screen
  appearance — no cleanup needed.

✅ Archiving — because RESTRICT forbids deletion

The Stage 03 constraint forces the Stage 04 design.

Stage 03 put ON DELETE RESTRICT on sale_lines.product_id. That means: 

sqlite> DELETE FROM products WHERE id = 2;
Error: FOREIGN KEY constraint failed

The product has been sold. Deleting it would orphan the
sale line. The database refuses.

This is correct. But an admin still needs a way to say "we no longer sell this." That's what archived_at does:

@app.route("/api/products/<int:pid>/archive", methods=["POST"])

               SET archived_at = ?, updated_at = ?

How archiving shows up:

  In the POS catalog query:

    GET /api/products
    → WHERE quantity > 0
       AND archived_at IS NULL

    Archived products don't appear. The
    cashier can't sell them. Correct.

  In sales history:

    sale_lines joins products by id.
    The archived product still exists.
    Old receipts still render it.
    Correct.

  In inventory's audit log:

    stock_movements still reference it.
    The archived product's history is
    intact. Correct.

  What the admin can't do:

    DELETE the product. RESTRICT forbids
    it. The only path to "remove from
    selling" is archive. The only path
    to "remove from history" is: nothing.
    History is immutable.

Why a timestamp, not a boolean:

  archived_at = '2026-11-14T15:30:00Z'

  vs.

  archived = 1

  The timestamp answers "when?" —
  which is useful for audit, for "how
  many products were archived this
  quarter," for "was this archived
  before or after the price change."

  The boolean only answers "is it
  archived?" and loses the when.

  Use the timestamp. If you need the
  boolean, it's `archived_at IS NOT NULL` —
  derived, not stored. Same principle as
  the rest of the build.

What if a product has stock and gets
archived?

  Nothing prevents it. The product is
  hidden from POS but still has 5 units
  in stock. Those units are invisible
  to the catalog.

  Is that right? It depends. Sometimes
  yes (discontinued item, don't sell it,
  but don't bother removing the stock).
  Sometimes no (should be zeroed first).

  A stricter version would refuse to
  archive a product with stock > 0:

    if product["quantity"] > 0:
        return jsonify({"error": "Zero the
        stock before archiving."}), 400

  Stage 04 doesn't add that guard —
  it's a policy decision, not a technical
  one. Mention it, let the reader decide.
  The lesson: archiving is a policy,
  not a technical default. Every store
  chooses its own.

✅ Migrations — upgrade in place

Stage 03 dropped and recreated. Stage 04 does not.

Stage 03's seed.py started with DROP TABLE IF EXISTS ... — fine for a fresh install, catastrophic for existing data. Stage 04 needs to add two columns to tables that already hold real rows. The pattern:

migrate.py 
def column_exists(conn, table, column):
    """SQLite doesn't have information_schema. Use PRAGMA."""
    cols = [r[1] for r in conn.execute(
        f"PRAGMA table_info({table})"
    ).fetchall()]
    return column in cols


def migrate(conn):
    """Apply Stage 04 migrations to an existing database."""
    applied = []

    if not column_exists(conn, "sales", "refund_of_sale_id"):
        conn.execute(
            "ALTER TABLE sales ADD COLUMN refund_of_sale_id INTEGER"
        )
        applied.append("sales.refund_of_sale_id")

    if not column_exists(conn, "products", "archived_at"):
        conn.execute(
            "ALTER TABLE products ADD COLUMN archived_at TEXT"
        )
        applied.append("products.archived_at")

    if applied:
        conn.commit()
        print("Migrations applied: " + ", ".join(applied))
    else:
        print("Schema is up to date — no migrations needed.")

    else:

Why PRAGMA table_info, not information_schema:

  SQLite is not a full SQL server. It doesn't
  have information_schema.columns like Postgres
  or MySQL. The equivalent is:

    PRAGMA table_info(table_name);

  which returns one row per column with:
    cid, name, type, notnull, dflt_value, pk

  We grab column 1 (name) and check for the
  column we're adding. If it's not there,
  ALTER TABLE ADD COLUMN. If it is, skip.

Why this pattern matters:

  Run migrate() on a fresh install:
    → Both columns missing → both ALTERs fire.
    → Schema is complete.

  Run migrate() on a Stage 03 database:
    → Both columns missing → both ALTERs fire.
    → Existing rows get NULL for the new
       columns. No data lost. Schema upgraded.

  Run migrate() again:
    → Both columns present → no ALTERs.
    → Idempotent. Safe to re-run.

  Run migrate() on a Stage 04 database:
    → Both present → no-op.

  Every path leaves a valid schema. That's
  what "idempotent migration" means.

What if ALTER TABLE fails halfway?

  In SQLite, ALTER TABLE ADD COLUMN is
  atomic — it either succeeds or fails as
  one operation. If the first ALTER succeeds
  and the second fails (extremely rare for
  ADD COLUMN), you'd have a half-migrated
  schema. The next run would ALTER only the
  missing column, completing the migration.

  This is acceptable for the POS. For a
  high-stakes system, you'd wrap the whole
  migration in a transaction (SQLite allows
  it — BEGIN; ALTER; ALTER; COMMIT;) or use
  a migration library like Alembic.

  We do the simpler version here. The lesson
  is the pattern (check-then-ALTER), not
  the ceremony around it.

Why we don't drop-and-recreate:

  Dropping sales would:
    → Lose every completed sale
    → Break every receipt
    → Lose every stock movement audit
    → Make the Z-report lose its history

  Stage 03's drop-and-recreate was honest
  for a tutorial. Stage 04's ALTER TABLE
  is honest for a real system. The shift
  from one to the other is the lesson.

The next migration would be:

  If Stage 05 (which doesn't exist) added
  sales.discount_total, seed.py would:

  schema evolution.

⚠️ Common mistakes

What to check if Stage 04 doesn't work.

1. Refunding by deleting the sale

Breaks every report that ever included it. Fix: reversal sale, original untouched, refund_of_sale_id points at it.

2. Double-refunding the same sale

Two reversal sales = customer gets double money back. Fix: check SELECT id FROM sales WHERE refund_of_sale_id = ? before refunding, return 409.

3. Refunding a refund

Refunding a sale that's itself a refund is nonsense — customer never paid that amount. Fix: check refund_of_sale_id IS NOT NULL, return 400.

4. Z-report summing only sales or only payments

The whole point is comparing two independent sums. If you compute one and derive the other, the check is tautological. Fix: compute SUM(grand_total) from sales AND SUM(amount) from payments separately.

5. Holding a sale with a stock check

Held carts would reserve inventory that might never be bought. Fix: hold validates product existence, not stock. Stock is checked at checkout.

6. Forgetting the print CSS

Printing on an 80mm printer without @page { size: 80mm auto } produces an A4 page with a tiny receipt in the corner. Fix: the full @media print block.

7. Deleting a sold product

RESTRICT refuses. Fix: archive with archived_at, not DELETE.

8. Drop-and-recreate on migration

Loses every existing sale. Fix: PRAGMA table_info check + ALTER TABLE ADD COLUMN. Idempotent.

❓ Frequently asked

Why is a refund a new sale instead of deleting the original?

Because financial records are immutable. If you delete a sale, every report that ever included it becomes wrong. A refund is a NEW sale with negative quantities and a negative payment, pointing at the original via refund_of_sale_id. The original stays untouched. Same for the stock movement — a refunded row with a positive delta, not a deleted sold row.

What does the Z-report actually reconcile?

Two independent sums for the day: net sales (SUM of grand_total on paid sales including refunds, so refunds subtract) and payments total (SUM of amount across all payment rows, refunds subtract too). If they match, the books match the money. If not, a sale or payment was written outside the checkout, or tampered with.

Why doesn't a held sale reserve stock?

Because a held sale is not a completed transaction. The customer hasn't paid. If holding reserved stock, an abandoned cart would lock inventory forever. Held sales are saved carts — no stock_movements, no quantity update. Stock is checked at checkout time, when the transaction becomes real.

What does the @media print CSS actually do?

Hides everything on the page except the open receipt modal, sizes the receipt to 80mm width, removes UI chrome (header, close button, print button), and sets @page { size: 80mm auto; margin: 0 } so the browser prints an 80mm page that ends where the content ends. The receipt was already styled monospace — the print CSS makes the paper metaphor real.

Why is product archiving needed instead of deletion?

Because Stage 03 put ON DELETE RESTRICT on sale_lines.product_id. You literally cannot delete a product that has been sold — the database refuses. The constraint forces the design. A nullable timestamp, archived_at: NULL means active, set means archived. Archived products disappear from the POS catalog but existing sale lines still render correctly.

What is the migration pattern and why does it matter?

PRAGMA table_info checks whether a column exists, ALTER TABLE ADD COLUMN adds it only if missing. Idempotent — running twice does nothing the second time. Unlike Stage 03's drop-and-recreate, this preserves existing data. The lesson: additive changes with existence checks. Drop-and-recreate works for a demo; ALTER TABLE with PRAGMA works for a database you can't lose.

Is this the final stage?

What should I build next?

Not another stage of this app. Either take a concept course (deployment, auth, POS hardware), or build something new that reuses this pattern. The four-stage arc — shell → client logic → backend → advanced data layer — applies to any transactional app: ticketing, subscriptions, booking, invoicing. Same three tables, same atomic checkout, same reversal-based refunds.

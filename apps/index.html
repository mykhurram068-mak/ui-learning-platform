The pattern: every build follows the same arc. Stage 01 is the static shell — layout, tokens, no logic. Stage 02 adds client-side state, derivation, and localStorage. Stage 03 moves data to Flask + SQLite, with atomic writes and a REST API. Stage 04 grows the advanced layer — transactions, pagination, reports, workflows, state machines. Four stages, each adds exactly one layer, then stops.

Why this shape: it mirrors how real software is built. The shell before the logic. The logic before the server. The server before the advanced concerns. Each stage is independently useful — you can stop after any one, ship it, and come back later.

What you'll learn across the builds

Each build teaches a different set of patterns. Together they cover the core of a modern web app.

Layout & design systems

CSS grid, flexbox, custom properties, dark mode, responsive breakpoints, shared tokens. Every build uses the same token set so the studio feels like one product.

Client-side state & derivation

One state object, one render(), everything else derived. Store facts, compute display. The pattern that runs through all five builds.

Flask + SQLite backends

REST APIs, foreign keys, atomic transactions, schema design, migrations. From a single-table app to a seven-table system.

Event logs & derived caches

Append-only event tables as source of truth. Derived caches (stock_movements, shifts, delivery_legs) kept in sync by transactions. The pattern that scales.

State machines & workflows

Valid transitions, invalid rejections, retry edges, approval workflows. The pattern for any app where "what state is this in" matters.

Reports & aggregates

SQL SUM, COUNT, GROUP BY, date ranges, pagination. Every build ends with at least one report that answers a real operational question.

Idempotency & correctness

Three-guard idempotency on every write. Price snapshots on sale lines. Reversal-based refunds. Atomic checkout. The discipline that makes an app trustworthy.

Multi-audience UX

Two views in HR (manager, employee). Three views in Delivery Tracking (customer, courier, dispatcher). One design system, multiple shapes.

How the four-stage arc works

Every build follows the same four stages. The domain changes; the arc doesn't.

01
Interface

Static HTML + CSS. Layout, tokens, sample data. No logic, no timers, no state. The shell that the rest of the build fills in.

02
Interactions

Client-side state, derived values, localStorage persistence. The app works, but only on one device and loses data on clear.

03
Backend

Flask + SQLite. The client's localStorage becomes fetch(). Three to five tables. Atomic writes. A REST API that's the source of truth.

04
Advanced

Transactions across multiple tables. Pagination, sorting, report queries. Workflows (retry, approval, bulk dispatch). Proof tables. The layer that turns the app into a system.

Each stage ships its own lesson page, its own working demo, and its own full source. You can start at any stage — if you already know HTML/CSS, skip to Stage 02. If you already know Flask, skip to Stage 04. No gate, no order enforced.

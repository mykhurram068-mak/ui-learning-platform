Stage 03 · 3–4 hours

Give it a memory.
Five tables. Atomic events. Public tracking.

The events move to SQLite. Five tables: customers, couriers, deliveries, delivery_events (append-only), delivery_legs (derived cache). The server runs the same state machine as the client and enforces it at the API. POST /api/deliveries/<id>/events does the event insert, the status update, and the leg refresh in one transaction. GET /api/track/<code> serves the customer page without auth, returning only the fields the customer needs.

Short answer: Five tables. customers, couriers, deliveries (with a UNIQUE tracking_code and a nullable courier_id), delivery_events (CASCADE, one row per fact), delivery_legs (CASCADE, one row per leg). The state machine is a Python dict mapping event types to the set of statuses they can transition from. A POST event does five things inside one transaction: validate, insert event, update delivery status, upsert current leg, return new state. The public tracking endpoint redacts PII and returns only the tracking code, destination, status, courier first name, and timeline.

The five tables

Three FKs. One event log. One derived cache.

Each table has one job. The customers and couriers are the actors. The deliveries table is the parcel. The events are the facts. The legs are the journey summary. Every table except deliveries uses CASCADE because they have no independent meaning without the delivery they describe.

CREATE TABLE customers (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  name       TEXT NOT NULL,
  email      TEXT NOT NULL UNIQUE,
  phone      TEXT,
  address    TEXT NOT NULL,
  created_at TEXT NOT NULL

CREATE TABLE couriers (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  name       TEXT NOT NULL,
  phone      TEXT,
  vehicle    TEXT NOT NULL DEFAULT 'van'
             CHECK (vehicle IN ('bike', 'car', 'van')),
  status     TEXT NOT NULL DEFAULT 'available'
             CHECK (status IN ('available', 'on_delivery', 'off_duty')),
  created_at TEXT NOT NULL
);

CREATE TABLE deliveries (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  tracking_code TEXT NOT NULL UNIQUE,
  customer_id   INTEGER NOT NULL,
  courier_id    INTEGER,
  origin        TEXT NOT NULL,
  destination   TEXT NOT NULL,
  status        TEXT NOT NULL DEFAULT 'pending'
                CHECK (status IN ('pending', 'assigned', 'picked_up',
                                  'in_transit', 'out_for_delivery',
                                  'delivered', 'failed', 'cancelled')),
  priority      TEXT NOT NULL DEFAULT 'standard'
                CHECK (priority IN ('standard', 'express')),
  created_at    TEXT NOT NULL,
  updated_at    TEXT NOT NULL,
  FOREIGN KEY (customer_id) REFERENCES customers(id) ON DELETE RESTRICT,
  FOREIGN KEY (courier_id)  REFERENCES couriers(id)  ON DELETE SET NULL
);
Why the machine is a Python dict, not a class:

  A class with a transition() method would
  work. But the state machine is data, not
  behavior. The transitions are a set of
  relationships between strings. A dict
  expresses that exactly.

  can_transition is the only function. One
  function, one dict. If the rules change,
  the dict changes, the function doesn't.
  If a new event type appears (like
  'reassigned' in Stage 04), add one line
  to TRANSITIONS and one line to
  EVENT_RESULT.

  This is the same shape as the JavaScript
  version. Different language, same data.

Why the sets, not lists:

  Sets give O(1) membership testing. For
  transitions like 'failed' that have four
  allowed from-statuses, checking is
  constant-time. Lists would be O(n) but n
  is small (4), so the difference is
  negligible.

  Sets also express intent: "these are the
  allowed values, order doesn't matter,
  duplicates don't exist." A list would
  suggest order is meaningful. It isn't.

Why can_transition returns False for
unknown event types:

  TRANSITIONS.get(event_type) returns None
  for an unknown type. None is not iterable,
  so 'current_status in None' would crash.
  The explicit None check returns False
  cleanly, so an unknown event type is
  rejected the same as an invalid
  transition.

  This is defense in depth. The API endpoint
  also has a CHECK constraint on the
  delivery_events.type column. An unknown
  type would fail at the INSERT. But
  can_transition failing first gives a
  cleaner error message ("cannot do that
  from this state" instead of "constraint
  violation").

Atomic event recording

Five writes. One transaction. Or nothing.

The event endpoint does more than insert a row. It also updates the delivery status and refreshes the current leg. All three writes must succeed or none should, or the database ends up with a delivery whose status doesn't match its events.

@app.route("/api/deliveries/<int:did>/events", methods=["POST"])
def record_event(did):
    data = request.get_json(silent=True) or {}
    event_type = data.get("type")
    note = (data.get("note") or "").strip() or None
    courier_id = data.get("courierId")

    if event_type not in EVENT_RESULT:
        return jsonify({"error": "Unknown event type."}), 400

    with get_db() as conn:
        delivery = conn.execute(
            "SELECT * FROM deliveries WHERE id = ?", (did,)
        ).fetchone()
        if not delivery:
            return jsonify({"error": "Delivery not found."}), 404

        if not can_transition(delivery["status"], event_type):
            return jsonify({
                "error": "Cannot " + event_type.replace("_", " ") +
                         " from status '" + delivery["status"] + "'."
            }), 409

        # The transaction: all writes inside `with get_db()`
        ts = now_iso()
        conn.execute(
            """INSERT INTO delivery_events
               (delivery_id, type, location, note, occurred_at, created_at, created_by)
               VALUES (?, ?, NULL, ?, ?, ?, 'api')""",
            (did, event_type, note, ts, ts),
        )

        new_status = EVENT_RESULT[event_type]
        conn.execute(
            "UPDATE deliveries SET status = ?, updated_at = ? WHERE id = ?",
            (new_status, ts, did),
        )

        if event_type == "assigned" and courier_id:
            conn.execute(
                "UPDATE deliveries SET courier_id = ? WHERE id = ?",
                (courier_id, did),
            )

        _refresh_current_leg(conn, did, event_type, ts)
        conn.commit()

        return jsonify(_delivery_payload(conn, did)), 201

Why the transition check reads delivery.status, not the events:

  The status field on deliveries is a cache
  of the last event's result. It's updated
  by this same endpoint, so it's always in
  sync with the event log.

  Reading status directly (one row lookup)
  is O(1). Deriving status from events (walk
  the log) is O(events). For the hot path of
  "record an event," the cache is what we
  want.

  This is the same trade-off as Inventory's
  products.quantity: cached field, kept in
  sync by the write path, used by the read
  path. The event log remains the source of
  truth if the cache ever needs to be
  recomputed.

Why 'assigned' has a courier_id side-effect:

  The event insert records the fact
  ("assigned"). The UPDATE records the
  consequence ("to courier 3").

  Two writes, one transition. They must
  both succeed or both fail. The `with
  get_db()` block guarantees it.

  An alternative would be a separate
  /api/deliveries//assign endpoint.
  That's also valid, but it would need to
  call record_event internally, which
  means the same transaction scope. One
  endpoint with a conditional side-effect
  is simpler.

Why 409 for invalid transitions:

  400 means the request is malformed (bad
  JSON, missing field). The client made
  a mistake.

  409 means the request is valid, but the
  server's current state doesn't allow it.
  The client sent a well-formed 'delivered'
  event, but the delivery is still pending.
  The state machine refuses.

  The client handles 409 differently from
  400: on 409, it shows "the delivery is
  still pending - pick it up first". On
  400, it shows a generic error.

  Same discipline as HR's clock-in and POS's
  checkout.

The transaction guarantee:

  Five writes for one event:
    1. INSERT delivery_events
    2. UPDATE deliveries.status
    3. UPDATE deliveries.courier_id (if assigned)
    4. INSERT or UPDATE delivery_legs
    5. UPDATE deliveries.updated_at (part of #2)

  If any fails, none commit. The invariant
  is: the delivery's status matches the
  last event's result, and the current leg
  matches the delivery's status. The
  transaction is what makes that invariant
  hold.

The legs cache

One row per journey segment. Derived from events.

The delivery_legs table is the cache that makes the tracking page fast. Each delivery has one or more legs. When an event arrives that ends a leg or starts a new one, _refresh_current_leg runs inside the same transaction. The tracking page reads legs directly, without walking events.

def _refresh_current_leg(conn, delivery_id, event_type, ts):
    """Update or close the current leg, and open a new one if needed."""
    current = conn.execute(
        """SELECT * FROM delivery_legs
           WHERE delivery_id = ? AND ended_at IS NULL
           ORDER BY leg_index DESC LIMIT 1""",
        (delivery_id,),
    ).fetchone()

    # Events that end the current leg
    ends_leg = event_type in ("picked_up", "in_transit", "delivered", "failed")
    # Events that start a new leg
    starts_leg = event_type in ("assigned", "picked_up", "in_transit")

    if current and ends_leg:
        conn.execute(
            "UPDATE delivery_legs SET ended_at = ?, status = 'completed' WHERE id = ?",
            (ts, current["id"]),
        )

    if starts_leg:
        next_index = (current["leg_index"] + 1) if current else 0
        conn.execute(
            """INSERT INTO delivery_legs
               (delivery_id, leg_index, from_location, to_location,
                started_at, ended_at, status)
               VALUES (?, ?, NULL, NULL, ?, NULL, 'active')""",
            (delivery_id, next_index, ts),
        )

Why legs are simpler than events:

  An event is a fact: "picked up at 9:14
  by courier Alex". Each event is one row,
  with a type and a timestamp.

  A leg is a summary: "the segment from
  'assigned' to 'picked_up' took 4 hours".
  Each leg is one row, with a start, an
  optional end, and a status.

  The event log has 4 events for delivery 1
  (assigned, picked_up, in_transit,
  out_for_delivery). The leg log has 3
  legs: assigned->picked_up,
  picked_up->in_transit, in_transit->out_for_delivery.

  The legs table is smaller. It's the
  summary the tracking page needs. The
  events table is the detail the audit log
  needs. Two shapes, two purposes, one
  source of truth (the events).

Why ends_leg and starts_leg are separate:

  Some events do both: picked_up ends the
  'assigned' leg and starts the 'picked_up'
  leg. Some events only end: delivered ends
  the last leg and doesn't start a new one.
  Some events only start: assigned starts
  the first leg.

  Splitting the logic into two checks makes
  the handling explicit. If an event type
  is added later (say 'arrived_at_facility'),
  the developer decides: does it end the
  current leg? Does it start a new one? The
  two sets make the answer visible.

Why leg_index increments from the last leg:

  Legs are sequential. The first leg is 0,
  the next is 1, and so on. The query
  ORDER BY leg_index DESC LIMIT 1 gets the
  highest-numbered leg (the current one).

  next_index = current.leg_index + 1 (or 0
  if there's no current leg). The new leg
  gets the next number.

  If a delivery is retried after a failure,
  the leg count grows. The history is
  preserved. 'Failed' ends a leg; the retry
  starts a new one with a higher index.
  Stage 04 will use this.

Why NULL locations in Stage 03:

  The legs table has from_location and
  to_location columns, but Stage 03 doesn't
  populate them. The schema is ready for
  Stage 04's map integration, where each
  leg will have real coordinates.

  Storing NULL now is honest: the data
  isn't known yet. Storing placeholder
  strings would be misleading. The
  columns exist for the shape Stage 04
  will fill in.

The atomicity guarantee:

  _refresh_current_leg is called inside the
  same `with get_db()` block as the event
  insert and the status update. If the leg
  insert fails (constraint, disk error), the
  whole transaction rolls back. The event
  isn't recorded, the status isn't updated,
  no leg is created.

  The legs cache is therefore never
  inconsistent with the events. It's either
  fully updated to reflect the new event,
  or fully unchanged. Same invariant as
  every previous transaction in the studio.

Public tracking - what to return, what to redact

Anyone with the code can see the timeline. Nobody sees PII.

The tracking page is public. The customer received a code, clicked a link, and sees the timeline. No login. The server responds to GET /api/track/<code> with a deliberately minimal payload.

@app.route("/api/track/<code>", methods=["GET"])
def track(code):
    with get_db() as conn:
        d = conn.execute(
            """SELECT d.tracking_code, d.destination, d.status,
                      c.name AS courier_name
               FROM deliveries d
               LEFT JOIN couriers c ON c.id = d.courier_id
               WHERE d.tracking_code = ?""",
            (code,),
        ).fetchone()

        if not d:
            return jsonify({"error": "Not found."}), 404

        events = conn.execute(
            """SELECT type, note, occurred_at
               FROM delivery_events
               WHERE delivery_id = (SELECT id FROM deliveries WHERE tracking_code = ?)
               ORDER BY occurred_at DESC""",
            (code,),
        ).fetchall()

    # Redact courier to first name + last initial
    courier = d["courier_name"] or "Unassigned"
    if courier != "Unassigned":
        parts = courier.split(" ")
        if len(parts) > 1:
            courier = parts[0] + " " + parts[-1][0] + "."

    return jsonify({
        "trackingCode": d["tracking_code"],
        "destination": d["destination"],
        "status": d["status"],
        "courier": courier,
        "events": [dict(e) for e in events],
    })

Why the SELECT lists specific columns:

  A SELECT * would return the delivery's
  internal id, customer_id, courier_id,
  priority, created_at, and updated_at.

  None of those should be in the public
  response. The customer doesn't need the
  internal id (the tracking code is the
  public key). The customer_id and
  courier_id would let an attacker enumerate
  other records. Priority is operational.
  Timestamps are useful but belong in the
  event log, not the header.

  Listing only the needed columns is
  defense by design. Even if someone later
  adds a 'customer_email' column to
  deliveries (which would be a bad design,
  but happens), the public endpoint won't
  leak it because it never selects it.

Why the courier name is redacted:

  The customer sees "Alex R." instead of
  "Alex Rivera". First name + last initial
  is enough for the customer to recognize
  their courier if they've interacted. The
  full name is unnecessary and could be
  used to look the courier up on social
  media.

  The redaction is server-side, not
  client-side. A client-side redaction
  (like the earlier version of this
  pattern) would send the full name over
  the wire; anyone inspecting the response
  in DevTools sees it. Server-side redaction
  means the full name never leaves the
  server.

Why the events query uses a subquery for
delivery_id:

  The event query needs the delivery's
  internal id, which we have from the
  first query (d doesn't include it after
  the SELECT list is trimmed).

  The subquery re-looks it up. It's an
  extra lookup per event request, but it
  keeps the response shape clean (no id
  in the payload). The alternative - two
  queries where the first returns the id -
  would work too, but requires the
  caller to have both queries open
  simultaneously.

  For a demo, the difference is negligible.
  For a hot path, you'd combine into one
  query with a JOIN.

Why this endpoint has no auth:

  The whole point of a tracking page is
  that the customer doesn't need an
  account. The tracking code IS the
  credential. It's long enough
  (DEL-XXXXXXXX) that guessing is
  impractical, and it's shared only with
  the customer.

  This is a "capability URL" pattern: the
  URL itself grants access, like a
  password-reset link. It's not as secure
  as auth, but it's the right choice for
  a public tracking page. The alternative
  (require the customer to log in) is a
  UX failure for a simple delivery.

  The lesson: match the security to the
  data. Tracking timeline for a parcel is
  low-sensitivity. Health records are not.
  The capability URL is right for one,
  wrong for the other.

async function recordEvent(deliveryId, eventType, note, courierId) {
  if (transitioning) return { ok: false, error: 'Processing' };
  transitioning = true;

  try {
    const res = await fetch(API + '/api/deliveries/' + deliveryId + '/events', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ type: eventType, note: note, courierId: courierId })
    });

    const body = await res.json();

    if (res.status === 409) {
      // State machine rejected the transition. Show the server's message.
      return { ok: false, error: body.error };
    }

    if (!res.ok) {
      return { ok: false, error: body.error || 'Request failed' };
    }

    // Server returns the full updated delivery; apply it locally
    applyDeliveryUpdate(body);
    return { ok: true };
  } catch (err) {
    return { ok: false, error: 'Network: ' + err.message };
  } finally {
    transitioning = false;
  }
}

Why 409 is treated as a specific case:

  The state machine on the server is the
  source of truth. When it rejects a
  transition, it sends a specific error
  message ("Cannot pick up from status
  'pending'"). That message is more useful
  than the client's own generic check.

  The client's canTransition is still useful
  for showing the right button. But when a
  user does something unexpected (opens
  two tabs, gets distracted, comes back),
  the server is the final authority. The
  client shows the server's message, not
  its own guess.

Why transitioning is cleared in finally:

  If the fetch throws (network error), the
  flag must still be cleared. Otherwise
  every subsequent event recording is
  rejected forever.

  This is the same pattern as every
  previous Stage 02 and Stage 03. The flag
  is set before the async work, cleared in
  finally. The window where it's true is
  exactly the window of the network
  request.

Why applyDeliveryUpdate vs applying the
full state:

  The server returns the full updated
  delivery, not the whole world. The client
  updates that one delivery in its local
  state and re-renders the affected views
  (courier button, dispatcher table row,
  customer timeline if visible).

  The alternative - refetching all
  deliveries after every event - is one
  extra round-trip per event, which is
  fine for a demo but unnecessary. The
  server's return value is the full
  delivery; use it.

Why the client still derives status:

  The courier's button needs to update
  instantly (before the server responds).
  The client derives status from its local
  events, shows the optimistic button state,
  then the server's response reconciles.

  This is optimistic UI: assume success,
  show the result, roll back if the server
  disagrees. Stage 03 does a simpler
  version: the client waits for the server,
  then renders. Stage 04 could add
  optimistic UI as a refinement.

  The principle: for the parts of the UI
  that must be instant (the button, the
  badge), the client derives. For the
  parts that must be correct (the timeline,
  the KPI counts), the server derives. Both
  derive from the same events, so they
  agree.

Next: Stage 04 - Advanced (Final)

Proof of delivery. Failed workflow. Bulk dispatch. Reports.

Stage 03 gives the app a memory. Stage 04 turns it into a real system:

  • Proof of delivery - a sixth table, proof_of_delivery, with photo or OTP evidence. One row per completed delivery. The evidence is its own table because it's referenced by audits, not by the operational dashboard.
  • Failed-delivery workflow - a delivery that fails can be retried without becoming a new delivery. The state machine gains a 'retry' concept. The legs table shows the failed attempt and the retry.
  • Bulk dispatch - assign 20 deliveries to a courier in one transaction. Either all 20 succeed or none do. The same atomicity lesson as POS checkout, applied to a batch.
  • Live map polling - the dispatcher dashboard refreshes every 30 seconds. GET /api/deliveries/active returns all active deliveries with their current leg joined, in one response.
  • Customer notification queue - a stub table, not sent, but the pattern is real. When a delivery transitions, a notification row is queued. A separate worker would send it. Stage 04 shows the queue, not the sender.
  • Reports - deliveries per courier per day, average delivery time, failure rate. Computed in SQL, not JavaScript. The same Z-report pattern from POS and timesheet pattern from HR.
  • Closeout - four stages, six tables, event log, state machine, atomic writes, public tracking, proof of delivery, bulk dispatch, reports. No Stage 05.

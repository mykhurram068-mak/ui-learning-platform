Build a delivery tracking app.
Shell, client, server, advanced.

A complete delivery tracking app in four stages. Start with a static three-view shell — a public customer tracking page, a mobile courier event view, and a dispatcher dashboard with a map and active table. Add a client-side state machine, derived delivery status from an event log, and localStorage. Move to Flask + SQLite with five tables: customers, couriers, deliveries, delivery_events, and a derived delivery_legs cache. Then grow: proof of delivery, failed-delivery workflow, bulk dispatch, live map polling, and reports. The same four-stage arc as the CRM, Inventory, POS, and HR builds — shell, client logic, backend, advanced data layer. Each stage adds exactly one layer and stops.

~13–15 hours Intermediate HTML · CSS · JavaScript · Python · Flask · SQLite 4 stages

What you end up with: a working delivery tracking system — customer-facing public tracking pages, a mobile courier view for logging delivery events, and a dispatcher dashboard for assigning couriers and monitoring active deliveries. A Flask + SQLite backend with five tables and an atomic event-log write that updates delivery status, refreshes the current delivery leg, and enforces the state machine. Proof-of-delivery evidence, failed-delivery handling, bulk dispatch, and daily reports. Runs on your laptop with three commands.

What it is not: real-time WebSocket updates, offline sync for couriers, real map tile integration, or a production-grade notification service. Those are separate concept courses, not Stage 05.

The data model

Five tables, three foreign keys, one event log.

customers who ordered it
├── id
├── name
├── email UNIQUE
├── phone
└── created_at

couriers who delivers it
├── id
├── name
├── phone
├── vehicle 'bike' | 'car' | 'van'
└── status 'available' | 'on_delivery' | 'off_duty'

deliveries the parcel
├── id
├── tracking_code UNIQUE (public key, e.g. DEL-8F3A2B)
├── customer_id FK to customers
├── courier_id FK to couriers (nullable until assigned)
├── origin
├── destination
├── status 'pending' | 'assigned' | 'picked_up'
│ | 'in_transit' | 'out_for_delivery'
│ | 'delivered' | 'failed' | 'cancelled'
├── priority 'standard' | 'express'
├── created_at
└── updated_at

delivery_events append-only log of what happened
├── id
├── delivery_id FK to deliveries ON DELETE CASCADE
├── type 'assigned' | 'picked_up' | 'arrived_at_facility'
│ | 'out_for_delivery' | 'delivered' | 'failed'
│ | 'gps_ping' | 'note'
├── location (lat,lng or address string)
├── note
├── occurred_at ISO timestamp
├── created_at
└── created_by 'courier:42' | 'dispatcher' | 'system'

delivery_legs derived cache of the current journey
├── id
├── delivery_id FK to deliveries ON DELETE CASCADE
├── leg_index INTEGER (0 = pickup leg, 1 = transit, ...)
├── from_location
├── to_location
├── started_at
├── ended_at NULL while the leg is current
└── status 'active' | 'completed' | 'failed'

(Stage 04 adds proof_of_delivery as the sixth table)

Why the event log

A delivery is a sequence of facts: picked up at 9:14, out for delivery at 14:05, delivered at 15:47. Each fact has a timestamp. Editing them destroys the history. The event log preserves it.

Why delivery_legs exists

It's a cache. Walking every event for every delivery on every page load is slow. One row per leg answers "where is it in its journey" in one query. Same trade-off as shifts in HR.

Why CASCADE, not RESTRICT

An event has no meaning without its delivery. Delete the delivery, the event log goes too. This is the opposite of HR's payroll events, which must survive employee deletion.

Why tracking_code is separate

The customer uses it without login. It can be human-readable (DEL-8F3A2B) while the internal id stays an integer. The code doesn't leak volume (the "4,728th delivery").

The three audiences

Customer, courier, dispatcher. One design system.

Customer

Public. Not logged in. Tracking on a phone. The page has one job: show where the parcel is, in plain English. No navigation, no settings, no sidebar.

Courier

In a car, on a phone, often one-handed. The primary action is one unmissable button: "I delivered this." The event log is a tap, not a form.

Dispatcher

At a desk. Manages 50 deliveries at once. Needs a map, a table, and the ability to assign a courier in two clicks. Information-dense by design.

Why three layouts

A single layout that serves all three is a compromise. The customer sees noise. The courier sees too many buttons. The dispatcher loses the density they need.

What you build, stage by stage

A concrete picture of the app at each point.

After Stage 01
A three-view shell. Customer sees a centered card with a code input and a sample timeline — nothing works. Courier sees a delivery card with three big buttons that do nothing. Dispatcher sees KPIs, a map placeholder, and a hardcoded table. The tab toggles between views.
After Stage 02
The shell is alive. Enter a tracking code → the timeline derives from the event log. Courier logs an event → the delivery's status changes, and the state machine rejects invalid transitions. Dispatcher assigns a courier → the delivery moves from pending to assigned. Everything persists in localStorage.
After Stage 03
The same UI, now talking to Flask. Events persist in SQLite. The delivery_legs cache updates atomically with each event. The public tracking endpoint returns the timeline without auth. The state machine is enforced at the API — you can't jump from pending to delivered. Concurrent event recordings are deduplicated.
After Stage 04 — complete
The full system. Proof of delivery with photo or OTP. Failed deliveries that can be retried without becoming new deliveries. Bulk dispatch. Live map polling. A notification queue stub. Daily reports: deliveries per courier, average delivery time, failure rate. The build is finished.

Where to go after Stage 04.

The Delivery Tracking build is four stages and it will be complete. Real-time WebSocket updates, offline sync for couriers, real map tile integration, and production-grade notification services are separate concept courses. They apply to any delivery app, not just this one.

Deploying Flask + SQLite
Gunicorn, reverse proxy, backups, and the SQLite concurrency question. From laptop to server.
Real-time with WebSockets
Server push, pub/sub, reconnection, and the patterns that replace polling. Delivery tracking is the canonical example.
Offline-first & sync
Service workers, IndexedDB, sync queues, conflict resolution. For couriers who lose signal in a tunnel.

Build a delivery tracking app.
Shell, client, server, advanced.

A complete delivery tracking app in four stages. Start with a static three-view shell — a public customer tracking page, a mobile courier event view, and a dispatcher dashboard with a map and active table. Add a client-side state machine, derived delivery status from an event log, and localStorage. Move to Flask + SQLite with five tables: customers, couriers, deliveries, delivery_events, and a derived delivery_legs cache. Then grow: proof of delivery, failed-delivery workflow, bulk dispatch, live map polling, a notification queue, and reports. The same four-stage arc as the CRM, Inventory, POS, and HR builds — shell, client logic, backend, advanced data layer. Each stage added exactly one layer and stopped.

~13–15 hours Intermediate HTML · CSS · JavaScript · Python · Flask · SQLite 4 stages · complete

What you end up with: a working delivery tracking system — customer-facing public tracking pages, a mobile courier view for logging delivery events, and a dispatcher dashboard for assigning couriers and monitoring active deliveries. A Flask + SQLite backend with seven tables and an atomic event-log write that updates delivery status, refreshes the current delivery leg, and enqueues notifications. Proof-of-delivery evidence, failed-delivery retry handling, bulk dispatch, live map polling, and daily reports. Runs on your laptop with three commands.

What it is not: real-time WebSocket updates, offline sync for couriers, real map tile integration, or a production-grade notification sender. Those are separate concept courses, not Stage 05.

The four stages

Each stage added exactly one layer. Stage 04 was the last one.

🚚
Stage 01
Interface
Done

The static shell. Three audiences, three layouts: a public customer tracking page (centered card, tracking code input, event timeline), a mobile courier event view (delivery detail card, one big primary action button, two smaller secondary actions), and a dispatcher dashboard (4 KPI cards, map placeholder, active-deliveries table). One shared design system. No data, no logic, no timers.

2–3 hours · HTML · CSS
⚡
Stage 02
Interactions
Done

Make it work. The customer tracking page derives its timeline from an event log. The courier view logs events that change the delivery's state — the state machine (pending → assigned → picked_up → in_transit → out_for_delivery → delivered) is enforced client-side. The dispatcher can assign a courier. Tapping "delivered" twice does not create two events. Everything persists in localStorage.

3–4 hours · JavaScript · DOM · localStorage · state machine
🐍
Stage 03
Backend
Done

Give it a server. Flask + SQLite. Five tables — customers, couriers, deliveries, delivery_events (append-only), delivery_legs (derived cache) — with three foreign keys. The core lesson: atomic event recording. A single POST appends the event, updates the delivery status, and refreshes the current leg, all in one transaction. The state machine is enforced at the API. A public tracking endpoint serves the customer page without auth, returning only the necessary fields.

3–4 hours · Python · Flask · SQLite · event log · state machine
📊
Stage 04 · FINAL
Advanced
Done

Make it a real system. Proof of delivery — a sixth table, one row per completed delivery, photo or signature or OTP evidence. Failed-delivery workflow — a delivery that fails can be retried without becoming a new delivery. Bulk dispatch — assign 20 deliveries to a courier in one transaction. Live map polling — the dispatcher dashboard refreshes every 30 seconds. Customer notification queue — a seventh table, records intent without sending. Reports — deliveries per courier, average delivery time, failure rate. This was the final stage.

3–4 hours · SQL · Flask · reports · workflow

The data model

Seven tables, four foreign keys, one event log.

customers who ordered it
├── id
├── name
├── email UNIQUE
├── phone
├── address
└── created_at

couriers who delivers it
├── id
├── name
├── phone
├── vehicle 'bike' | 'car' | 'van'
├── status 'available' | 'on_delivery' | 'off_duty'
└── created_at

deliveries the parcel
├── id
├── tracking_code UNIQUE (public key, e.g. DEL-8F3A2B)
├── customer_id FK -> customers RESTRICT
├── courier_id FK -> couriers SET NULL
├── origin
├── destination
├── status 8 states, CHECK constrained
├── priority
├── created_at
└── updated_at

delivery_events append-only log of what happened
├── id
├── delivery_id FK -> deliveries CASCADE
├── type 'assigned' | 'picked_up' | 'in_transit'
│ | 'out_for_delivery' | 'delivered' | 'failed' | 'note'
├── location
├── note
├── occurred_at
├── created_at
└── created_by

delivery_legs derived cache of the current journey
├── id
├── delivery_id FK -> deliveries CASCADE
├── leg_index (0, 1, 2, ...) grows on retry
├── from_location
├── to_location
├── started_at
├── ended_at NULL while current
└── status 'active' | 'completed' | 'failed'

proof_of_delivery evidence, when delivered
├── id
├── delivery_id FK -> deliveries CASCADE UNIQUE
├── method 'photo' | 'signature' | 'otp'
├── reference
├── note
├── captured_at
└── captured_by

notifications queued, never sent by the app
├── id
├── delivery_id FK -> deliveries CASCADE
├── type 'out_for_delivery' | 'delivered' | 'failed'
├── recipient
├── status 'pending' | 'sent' | 'failed'
├── created_at
└── sent_at

Why the event log

A delivery is a sequence of facts. Each has a timestamp. Editing them destroys the history. The event log preserves it. Same principle as HR's attendance events.

Why delivery_legs exists

It's a cache. Walking every event for every delivery on every page load is slow. One row per leg answers "where is it in its journey" in one query.

Why proof is its own table

Evidence is a distinct fact, queried by auditors separately from operational data. UNIQUE on delivery_id enforces one proof per delivery without nullable columns in the deliveries table.

Why notifications are queued

Recording intent is not sending. A failed email can't roll back a successful delivery. The queue is the seam between the operational app and the notification worker.

The three audiences

Customer, courier, dispatcher. One design system.

Customer

Public, no login. Tracks on a phone. The page has one job: show where the parcel is, in plain English. The tracking code is the capability.

Courier

In a car, on a phone, often one-handed. One unmissable primary button. The event log is a tap, not a form. Proof of delivery is a quick modal.

Dispatcher

At a desk. Manages 50 deliveries at once. A map, a table, bulk actions. Live polling every 30 seconds, no WebSocket complexity.

Why three layouts

A single layout that serves all three is a compromise. The customer sees noise. The courier sees too many buttons. The dispatcher loses the density they need.

What you built, stage by stage

A concrete picture of the app at each point.

After Stage 01
A three-view shell. Customer sees a centered card with a code input and a sample timeline. Courier sees a delivery card with three big buttons that do nothing. Dispatcher sees KPIs, a map placeholder, and a hardcoded table. The tab toggles between views.
After Stage 02
The shell is alive. Enter a tracking code → the timeline derives from the event log. Courier logs an event → the delivery's status changes, and the state machine rejects invalid transitions. Dispatcher assigns a courier. Everything persists in localStorage.
After Stage 03
The same UI, now talking to Flask. Events persist in SQLite. The delivery_legs cache updates atomically with each event. The public tracking endpoint returns the timeline without auth. The state machine is enforced at the API — you can't jump from pending to delivered.
After Stage 04 — complete
The full system. Proof of delivery with photo or OTP. Failed deliveries that can be retried without becoming new deliveries. Bulk dispatch. Live map polling. A notification queue stub. Daily reports: deliveries per courier, average delivery time, failure rate. The build is finished.

What you'll learn

The concepts, grouped by stage.

Stage 01 — Layout

Three independent layouts sharing one design system. The customer tracking page and dispatcher dashboard have nothing structurally in common. Same CSS tokens, different grids.

Stage 02 — State machine

One state object. One TRANSITIONS map. One deriveDeliveryStatus. Three idempotency guards. The first build in the studio where the state graph is the central concept, not a supporting pattern.

Stage 03 — Event log + atomic writes

Append-only events as source of truth. A derived delivery_legs cache. Server-side state machine. A single POST endpoint that writes to four tables atomically. Public tracking without auth.

Stage 04 — Workflow & operations

Proof of delivery as its own table. Failed retry as a new edge in the state graph. Bulk dispatch as a single transaction. Live polling without WebSockets. Notification queue as a decoupling seam. Reports as SQL aggregates.

Where to go after Stage 04.

The Delivery Tracking build is four stages and it's complete. Real-time WebSocket updates, offline sync for couriers, real map tile integration, and production-grade notification senders are separate concept courses — they apply to any delivery app, not just this one.

Deploying Flask + SQLite
Gunicorn, reverse proxy, backups, and the SQLite concurrency question. From laptop to server.
Real-time with WebSockets
Server push, pub/sub, reconnection, and the patterns that replace polling. Delivery tracking is the canonical example.
Offline-first & sync
Service workers, IndexedDB, sync queues, conflict resolution. For couriers who lose signal in a tunnel.

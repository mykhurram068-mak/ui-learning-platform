Short answer: One HTML file, two top-level layouts. Manager view: a grid with KPI cards on top, employee list on the left, today's attendance timeline on the right. ✅ Two views, one app

A manager dashboard. An employee button. Different jobs, same design system.

Most web apps have one audience. HR & Attendance has two, and they don't overlap:

The manager

Needs to see who's working, who's late, who's over hours. Needs to approve timesheets and correct mistakes. Sits at a desktop, glances at the app ten times a day. Values density and scanability.

The employee

Needs to clock in when they arrive and clock out when they leave. Stands at a kiosk or holds a phone. Uses the app twice a day. Values speed and zero friction.

Why one shell can't serve both

A dashboard is the wrong shape for a clock-in button — too many decisions. A giant button is the wrong shape for the manager — too little information. Trying to be both makes both worse.

The shared system

Same color palette, same radii, same font stack, same input styles. A manager tabbing between views feels the same app. An employee seeing the manager view (unlikely) recognizes the visual language. The tokens are the unity; the layouts diverge.

The tab bar sits at the top of both views. It's the only navigation. It flips between #view-manager and #view-employee via a CSS class on the body. In Stage 02, the tab will persist the active view in localStorage so the employee who clocked in last time lands back on the employee view next session.

✅ The manager layout

KPIs on top, list left, timeline right.

KPI row (top)

Four cards: Clocked in now, Hours today, Pending approvals, Active employees. Each shows a big number and a small context line below.

Employee list (left)

Six employees. Each row: avatar, name, role, current status ("Working since 9:02" / "Off" / "On break"). A colored dot on the left encodes status at a glance.

Timeline (right)

Today's events in reverse chronological order. Each row: timestamp, employee name, event type (clock-in / break / clock-out), and a small icon. Scrolls independently.

Two-column grid

Below the KPIs, a 2-column grid: list takes 1fr, timeline takes 1fr. On narrow screens, they stack.

The manager layout is a 3-row grid: header, KPI row, content. The content row is a 2-column grid. Here's the CSS shell — the whole layout fits in 18 lines:

The four cards tell a story: who's here now, how much work happened today, what needs a decision, and who's on the team. The first two are live numbers that update; the third is a queue; the fourth is a constant. Every manager dashboard can be reduced to those four questions, and these four cards are the answers. Stage 02 makes the numbers live; the shape doesn't change.

✅ The employee layout

One button. One number. No decisions.

The employee view is what the employee sees when they tap "Employee view" at the top — or, in a real kiosk deployment, what's shown on the tablet by the door. It has exactly four elements:

Big clock

The current time, in monospace, in a large font. The employee needs to know what time it is — it's the answer to "am I late?"

Status

"Not clocked in" / "Working since 9:02" / "On break since 12:15". One line, plain English, no jargon.

The button

One giant button that says "Clock in" or "Clock out" or "End break" depending on current state. Full width, tall, high contrast.

Today's hours

A small line under the button: "Today: 4h 12m". In Stage 02, this updates live as the clock ticks.

The employee layout is centered — the card sits in the middle of the screen with generous whitespace around it. Here's the CSS:

Why data-type instead of a class: the type drives both the icon color (CSS: .hr-event[data-type="in"] { color: var(--success) }) and, in Stage 02, the click handler's branching logic. One attribute, two purposes. A class could do the CSS half, but the JS would need the class too — and class names are easier to change than data attributes when the design updates. Keep data in data-*; keep appearance in classes.

Why data-type values are in / break-start / break-end / out, not clock-in: shorter, and they match the enum in the database schema (which we'll write in Stage 03). One vocabulary across the whole app. If the schema says type = 'in', the HTML says data-type="in". No translation layer, no bugs from mismatched strings.

✅ Shared tokens — what makes it one app

Two layouts, one design system.

The two views share only CSS custom properties. Every color, radius, spacing step, and font size is a token. The layouts diverge; the tokens don't.

The tokens are identical to Inventory and POS. That's intentional. Every app in the studio shares the same visual identity — same slate palette, same cyan accent, same semantic greens and reds. A manager tabbing between HR, POS, and Inventory feels one product, not three. The tokens are the brand.

--header-h: 56px is new. POS used it as --topbar-height, HR uses it as --header-h. Same value, different name — each app names it for its own context. Both views' grid rows reference this token, so changing the header height is one line, not two.

✅ The full file

The complete shell. Delivered separately so this page stays readable.

The full shell is hr-stage-01.html — one HTML file, ~280 lines, no dependencies, no JavaScript beyond the tab toggle. It's delivered as a separate message (see the "Continue the build" section below for how to request it), so this lesson page stays focused on the concepts and the snippets.

The file contains:

  • The -- token block (identical to the other apps)
  • The header bar with brand, page title, and the manager/employee tab toggle
  • The manager view: 4 KPI cards, 6 employees, 8 timeline events, all hardcoded
  • The employee view: clock card with current time, status, big button, today's hours
  • The CSS for both layouts (grid for the manager, centered flex for the employee)
  • The CSS for shared components: cards, rows, badges, the button
  • A 15-line inline script that wires the tab toggle (adds/removes a class on the body)

No data loads, no timers, no storage. Stage 01 is a layout exercise, and the full file is the exercise's answer.

➡️ Next: Stage 02 — Interactions

The clock actually ticks.

Stage 02 makes the shell alive. The KPI numbers recompute from the event list. The employee clock ticks once per second. Clocking in creates a real event, updates the KPI, and starts the "Working since" timer. Clocking out closes the shift, computes the hours worked, and adds them to the daily total. Everything persists in localStorage.

The four big lessons in Stage 02:

  • A single state object — { employees: [], events: [], view: 'manager' }. Everything else derives from it.
  • Derived KPIs — the four card numbers are computed from the event list on every render, never stored.
  • Idempotent clock-in — clicking "Clock in" twice must not create two events. The button disables during the transition, and the handler checks the state before mutating.
  • A live clock — the current time updates once per second via setInterval. Cleaned up on tab close. The employee card's "Working for 4h 12m" recomputes every tick.

Stage 02 ships the full file too — hr-stage-02.html, ~750 lines. Same split: the lesson page here (with snippets), the full file there.

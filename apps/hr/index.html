Build an HR & attendance app.
Shell → client → server → advanced.

A complete HR & attendance app in four stages. Start with a static two-view shell — a manager dashboard and an employee clock-in page. Add a live clock, idempotent clock-in/out, derived KPIs, and localStorage. Move to Flask + SQLite with an event-log attendance model and a derived shifts table. Then grow: timesheets with overtime, manual corrections, a roster, manager approval, and reports. The same four-stage arc as the CRM, Inventory, and POS builds — shell, client logic, backend, advanced data layer. Each stage adds exactly one layer and stops.

~12–14 hours Intermediate HTML · CSS · JavaScript · Python · Flask · SQLite 4 stages

What you end up with: a working HR & attendance app — employees, an append-only event log of clock-ins, outs, and breaks, a derived shifts table that pairs events into shifts, and a manager dashboard that shows who's working, who's late, and how many hours have accumulated. A timesheet view with overtime. Manual corrections that never edit history. A roster that compares "should have worked" against "did work." A manager approval workflow that locks a week's timesheet. Runs on your laptop with three commands.

What it is not: authentication, payroll export, timezone/DST handling, hardware integration. Those are separate concept courses, not Stage 05.

🗄️ The data model

Three tables, two foreign keys, one event log.

employees
├── id
├── name
├── email UNIQUE
├── role 'employee' | 'manager'
├── hourly_rate
├── hired_at
└── archived_at ← NULL = active, set = former employee

attendance_events ← the third table. Append-only. Never edited.
├── id
├── employee_id FK → employees.id ON DELETE RESTRICT
├── type 'in' | 'out' | 'break_start' | 'break_end'
│ | 'manual_in' | 'manual_out'
├── occurred_at ISO timestamp (UTC)
├── note ← for manual events, the reason
└── created_at ← when the row was written

shifts ← the pairing layer. Derived from events, cached.
├── id
├── employee_id FK → employees.id ON DELETE RESTRICT
├── date 'YYYY-MM-DD' (start date, even for overnight shifts)
├── clock_in_at
├── clock_out_at ← nullable while the shift is open
├── break_minutes
├── minutes_worked
└── status 'open' | 'closed' | 'approved'

Why event log, not mutable shifts

Events are facts. Facts don't get edited. A missed clock-out is fixed by adding a manual_out event with a note, not by updating a row. The audit trail survives. Same principle as POS refunds.

Why shifts exists at all

It's a cache. The derivation (pair in with out, subtract breaks) is correct but slow to run on every page load. Cache the result, recompute on every event. Same trade-off as products.quantity in Inventory.

Why RESTRICT on events

An employee who has clocked in cannot be deleted. Their attendance is a payroll record. Archive them instead — same pattern as POS products that have been sold.

Why no timezone yet

All times are UTC, and the app assumes one timezone. DST and multi-timezone support are a concept course, not a stage. Store UTC, convert at display — the rule, deferred.

📦 What you build, stage by stage

A concrete picture of the app at each point.

After Stage 01
A two-view shell. Manager sees KPIs, a list, and a timeline — all hardcoded. Employee sees a clock card with a big button. Tab toggles between views. Nothing works.
After Stage 02
The shell is alive. Clock in → status flips, KPI updates, timer starts. Clock out → hours computed, added to today. The employee view's button label changes by state. Everything persists in localStorage. Still single-device, still no server.
After Stage 03
The same UI, now talking to Flask. Events persist in SQLite. The shifts table is derived from events server-side. Clock-in is idempotent — the same employee can't have two ins without an out between them. Overnight shifts, break pairing, and edge cases handled.
After Stage 04 — complete
The full app. Timesheet view — a week grid with hours and overtime. Manual corrections as new events, with a note and a timestamp. A roster comparing scheduled vs worked. Manager approval — approve a week, timesheets lock, corrections require a re-open. An attendance report. The build is finished.

🔐 Authentication & sessions
Password hashing, session cookies, roles. The role field in employees becomes a real auth boundary.
⏱️ HR concepts — time & payroll
Timezone/DST handling, payroll exports, overtime jurisdictions, labour law constraints. HR-specific, taught standalone.

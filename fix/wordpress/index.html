❓ Frequently asked questions

Are these fixes safe to run on a live site?

Every fix lists the risk level. The "deactivate plugins" approach is always safe. Fixes that touch the database are marked and include a backup step first. If a fix would take down a live site, we say so upfront.

Do these work with WordPress multisite?

Most do. Fixes that differ on multisite are marked with a "Multisite" note. Network-activated plugins work differently from site-activated plugins — the fix pages call this out.

What about classic themes vs block themes?

Where the fix differs, we cover both. Theme CSS issues are common to both; child theme fixes have block-theme-specific notes when they matter. Block themes don't use style.css the same way, and the fix pages explain this.

Do you cover page builders like Elementor, Divi, Bricks?

Only when the fix is builder-agnostic. Page-builder-specific issues are their own ecosystem and there are already good resources for those. We focus on the WordPress core problems underneath.

Why not just use WP-CLI for everything?

WP-CLI is great when you have it. But most developers don't have shell access on shared hosting. Every fix page includes both the WP-CLI command (when applicable) and the file-manager/admin alternative.

Is this a replacement for WordPress support?

No. For plugin-specific bugs, the plugin author's support forum is still the right place. These pages help you identify which plugin is at fault and how to work around it while waiting for the developer.
